# Authorization 拥有授权版本存储

## 状态

已接受。

## 背景

授权版本用于使权限、角色、菜单、数据范围、密码或用户状态变化前签发的 Token 失效。
它原先存放在 Identity 的 `users.token_version`，使用户身份资料与 Authorization 的会话失效
规则耦合。切换事实来源还必须兼顾存量 Token 兼容、短期回滚和 GORM AutoMigrate 的列管理。

## 决策

Authorization 拥有 `user_access_versions`，该表是 Access Token 和 Refresh Token 授权版本的
唯一读取事实来源。Identity 继续负责 Token 解析、签名、Redis 黑名单以及用户存在性和启用
状态，但不拥有授权版本的初始化、读取、比较或提升。

从旧字段切换到新表时采用停机切换：停止全部旧实例和写流量，完成迁移与校验，再启动新版本
并恢复流量。旧实例只维护旧字段而新实例只读新表，因此两个版本不得混跑；不采用双读取最大值
或长期回退旧字段的滚动兼容方案。

观察期结束后的退出顺序固定为：

1. 先停止镜像写。
2. 移除全部运行时读写。
3. 从 User GORM Model 移除旧字段。
4. 从 AutoMigrate 的列声明中移除旧字段并验证启动。
5. 通过独立 DDL 删除 `users.token_version`。

不得先删列再发布退出版本，否则旧运行时 SQL 可能失败，AutoMigrate 也可能重新创建该列。

## 取舍

- 独立 MySQL 表比 Redis 授权版本具有更清晰的持久化和恢复语义，但每次认证需要读取持久化存储。
- 停机切换会产生短暂不可写窗口，但避免旧写入者与新读取者混跑造成授权版本过期。
- 观察期原子镜像增加短期写复杂度，但提供可验证的整体回滚路径；它不是长期双写架构。
- 独立删列步骤增加一次数据库变更，但将应用兼容性验证与不可逆 DDL 解耦，降低恢复风险。

## 实施结果

2026 年 7 月 31 日完成退出顺序：

1. 三小时加速耐久性资格验收和最终一致性扫描通过。
2. 退出版本停止旧字段镜像并移除全部运行时读写。
3. User GORM Model 与 AutoMigrate 不再声明 `users.token_version`。
4. 隔离真实 MySQL 已通过独立 DDL 删除旧列。
5. 迁移锁、回填、观察、旧版本回滚代码及
   `access_version_migration_states` 已退役并完成备份后删除。

因此 `user_access_versions` 现为唯一长期事实来源。应用只能回滚到仍读取新表且不依赖
旧列或迁移状态的版本；恢复旧字段需要新的独立架构与数据库变更，不能作为常规回滚。

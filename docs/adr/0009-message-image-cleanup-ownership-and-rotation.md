# 消息图片清理由 Files 持久化管理并排除未绑定轮转

## 状态

已接受（目标行为见 `openspec/changes/schedule-announcements-and-cleanup-message-images/`；部署仍受独占存储前提约束）。

## 背景

消息图片复用 Files 的 File Record 和对象存储定位，但由 Messaging 绑定到消息。原有过期清理先删记录再删对象，存储失败时会丢失定位；轮转也可能同时搬动未绑定图片。对象删除不可撤销，跨桶时仅靠对象同名无法证明归属。

## 决策

Files 拥有 `message_image_cleanup_jobs` 持久化队列；每个到期未绑定 File Record 在短事务内复核并登记完整原始位置，提交后删除受信对象，所有位置成功后在同一事务内物理删除 File Record 与队列。失败保留定位并限额重试，dead 保留人工处置。Messaging 只通过 Files 契约绑定和读取，不拥有清理队列或对象生命周期。

轮转候选排除全部未绑定消息图片及任何已登记清理对象；已绑定图片和普通文件沿用轮转。上线先停止旧实例并排空旧 Copy／反向 Move。跨桶清理仅适用于经部署核实的本应用独占 `message-images/UUID` 命名空间、无外部覆盖且非版本化、无 Object Lock 的存储；代码校验生成键格式与数据库归属冲突，但不能证明历史 bucket 的实际所有权。

`message_image_cleanup_jobs.retry_count` 的数据库不变量为 `0–24`，通过 MySQL `CHECK` 约束强制执行；发现已有非法历史值时迁移必须失败，不自动归一化为 `dead`，避免掩盖数据损坏。该约束以 MySQL `>= 8.0.16` 的真实执行语义为部署前提；低于此版本的实例不得启用本变更。集成门禁必须同时核对服务端版本和约束拒绝行为，不能仅依赖 SQLite 或 `mysql:latest` 标签。

## 取舍与后果

持久化队列比单次删除增加表、唯一索引与人工 dead 处置，却避免对象尚在而 File Record 已消失。排除未绑定轮转牺牲此类图片的冷热分层，换取清理与轮转的不交叠；不能用跨桶扫描代替部署归属核对。关闭轮转或更换 bucket 前仍须处理旧位置。回滚必须保留队列并先停止新实例；旧版本不理解队列的读取／绑定／轮转保护，不能带 pending/dead 直接运行。已删除对象无法通过 DDL 回滚。

# 组织管理

> 本文只保留组织模块边界和数据范围注意事项。接口契约以本地 `http://localhost:8080/docs` 与 `http://localhost:8080/docs/openapi.json` 为准；当前行为以 [`openspec/specs/organization-management/spec.md`](../../openspec/specs/organization-management/spec.md) 为准。

## 模块边界

`internal/organization` 负责组织单位、组织树、组织成员关系和资源 Scope 查询。

## 关键规则

- `parent_id=0` 表示根组织；组织编码全局唯一。
- 创建或修改组织时，父组织必须存在，且不能形成自引用或循环。
- 组织树按 `sort asc, id asc` 排序。
- 删除有子组织的节点或仍被普通角色当前`custom`引用的组织必须拒绝；停用／无成员角色不豁免，不自动改角色范围。合法删除清理成员关联，但若会实际移除本人或现存admin关联用户的归属，整次拒绝，admin角色停用不解除保护。
- 组织中心成员分配是完整覆盖，空列表清空但不豁免旧对象检查。正常目标须存在、未删除且在范围内；实际移除的软删普通旧成员允许在完整范围／本人／保护检查后受控清理。原有本人／受保护关系可原样保留以维护其他普通成员，保留行`joined_at`不重写。工作台逐人维护仍是保留不可管理关系的独立入口。
- 组织列表、组织树和成员查询均应用当前用户的数据范围。
- `self` 数据范围没有可见组织；树查询保留可见节点所需祖先，`manageable=false` 的祖先仅用于定位，不可读成员、移动或作为归属／自定义范围选择目标。
- 数据范围只限制可见数据，不替代 API 动态权限。
- 关联保护[历史证据](../reviews/evidence/protected-authorization-assignments-2026-10-17.json)保留；成员差量现已实施并完成[定向验收](../reviews/evidence/membership-delta-2026-10-18.json)：完整目标只增删差量，A/B→B/C仅提升A/C，B关系、物理`created_at`（业务`joined_at`）与版本保持，其他范围数据读取者不额外失效。合法等价整组不补／升版本；I4仍由独立change处理。

## 接口入口

Swagger UI 的 `organization` 标签提供：

- 组织单位列表、树、创建、修改、删除。
- 组织成员分配和查询。

规则变化以 OpenSpec 为准；本页不重复维护请求和响应示例。

## 工作台集成

路由为 `/organizations`、`/organizations/:id`、`/organizations/:id/move`。列表需要 `admin.organizations.get` 和 `admin.organizations.tree.get`，详情从受 `admin.organizations.tree.get` 保护的树定位可管理节点，成员读取另需 `admin.organizations.id.users.get`；移动需 `admin.organizations.id.put`。

树节点包含 `id,parent_id,name,code,remark,sort,status,manageable,children`。范围外祖先只是路径占位，不是授权目标。移动确认展示旧路径／新路径，由后端最终拒绝循环及越权。

加入／移除一名成员需要用户详情读取与 `admin.users.id.organizations.put`，候选用户列表另需 `admin.users.get`。先读取目标用户最新详情，在其可管理组织集合增删当前组织，再提交显式数组与 `expected_access_version`；不覆盖整组成员、不移除其他归属。409 必须重新读取核对，不显示成功或自动覆盖。隐藏归属、加入时间与受保护用户规则见 [用户管理](user-management.md)；实施中的新增契约见 [`组织 delta`](../../openspec/changes/build-admin-workbench/specs/organization-management/spec.md)。

逐人组织在同一事务先按既有Ensure规则初始化／锁定共享版本并检查CAS，再校验身份、保护、范围和原始引用，最后只比较当前可管理关系。合法无变化返回current；真实变化只提升目标一次，隐藏与保留关系时间不重写。缺行合法no-op可初始化为1，拒绝时该初始化回滚，与整组no-op不补行规则不同。清空可管理关系后若已失去目标可见性，后续空请求仍拒绝，不以no-op绕过范围。

## 组织拓扑写入与部署切换

创建组织、显式携带`parent_id`的修改和删除组织，在同一数据库事务内先按ID升序锁定当前有效父关系，再使用这份父图核验范围、父级存在性、循环或子组织，并提交写入。等待锁后不得复用旧RR快照作拓扑判断；范围与层级查询也复用事务内父图。未携带`parent_id`的普通属性修改不进入此拓扑协议。

现有权限规则不变：`manageable=false`祖先只能定位；创建根组织要求全范围，但可管理组织仍可合法移动到`parent_id=0`。I4已另外实现真正父边变化的有限范围根依赖失效，不将C4防环本身当作失效目标。

移动使用同一份锁定父图，取旧／新父级祖先链的对称差：共同祖先、0、移动节点及其后代自身范围根不因这条父边改变后代ID集合。Authorization经App提供最小ID能力，批量当前读取这些根的成员、原始用户角色关联与有序角色元数据，复核后选择适用的`org_and_children`角色依赖者；不能只枚举移动节点成员，也不能因另一角色`all`、重复角色或多个根使最终合并范围相同而豁免。

依赖读取、父边更新与去重升序用户版本在同一最外层事务内完成；等待后使用当前事实，重试每attempt重算，不增加重试类或次数。第二项版本失败也回滚父图和此前全部增量。仅展示字段、相同父级、普通`org/self/custom`固定范围与纯成员变化不由I4额外失效；成员变化继续只处理实际归属差量，不引入最终权限diff、缓存或新版本字段。

部署不需要DDL或数据迁移，但不能让新旧结构写入协议混跑：

1. 停止所有组织创建、带父级修改和删除，以及相关角色范围／启停／删除、组织成员写入，等待在途事务结束；完整参与者范围还须遵守下节引用生命周期要求。
2. 切换全部参与实例／入口到共同协议，确认不存在旧写入方或旁路引用写入后，再恢复写流量；不能仅替换组织PUT所在实例。
3. 回滚同样先停写、等待并整批切回；旧版本会重新暴露C4成环和I4漏失效风险，不降授权版本、不恢复已失效Token，不把滚动混跑视为安全回滚。

防环历史证据见[C4验收](../reviews/evidence/c4-organization-moves-fix-2026-10-17.json)；有限层级依赖见[I4新增90条观察](../reviews/evidence/organization-hierarchy-dependents-2026-10-18.json)，包含十二对真实HTTP交错、未过期Access／Refresh、第二用户回滚、真实Runner重试与缺版本行边界。I4 delta未同步、未归档；生产切换未在隔离验收中执行，不表示所有调度或整个C6完成。

## 引用生命周期协议与切换

组织成员整组替换、逐人组织PUT及custom引用建立也进入C4父图屏障。删除通过Authorization最小能力先收集操作者、当前成员和原始custom角色依赖，统一锁当前身份／角色后再核对范围及适用引用；等待后不沿旧RR快照决定删除。绑定先提交后删除包括新成员版本；删除先完成后两个成员入口均不得重建引用。

R4-R6没有新增DDL、全局锁表或FK级联，但部署停止范围不能只覆盖上述C4结构入口：

1. 停止全部实例的角色归属／权限／数据范围／菜单分配、相关角色与权限生命周期、组织成员写入、菜单与API绑定／停用／删除、受影响身份管理及适用Seed写入，等待在途事务结束。
2. 全部参与者切换到新协议后再恢复写流量；不能保留旧实例或旁路引用写入者。
3. 回滚同样停写、等待、整批切回；不自动恢复已经合法清除的引用，不把旧协议的竞争风险视为已解决。历史孤儿需另行核实，不自动修复。

隔离MySQL 8.0.19原程序、受控先后提交、回滚、保护与软删恢复证据见[生命周期验收](../reviews/evidence/authorization-reference-lifecycle-2026-10-18.json)。生产切换、全部历史数据及所有调度均未验证；成员差量／no-op与I4各有独立专项验收，不能把这些局部检查扩大为整个C6完成。

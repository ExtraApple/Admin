# 用户管理实施文档

> **文档定位**: 已实现模块的实现说明。认证行为以 `openspec/specs/auth/spec.md` 为准；文件上传安全 V1 已同步并归档，当前头像行为以 `openspec/specs/user-management/spec.md` 为准，历史设计和验收记录位于 `openspec/changes/archive/2026-07-16-harden-file-upload-security/`。

## 当前状态

用户管理是后台系统的核心模块，已完成 **注册、登录、个人信息管理、管理员用户管理** 四大板块。

## 模块目标

用户管理负责用户从注册到登录、从个人信息维护到管理员对用户的增删改查的全流程。

最终效果：

```text
用户访问
  ├── 获取验证码 → 注册账号
  ├── 获取验证码 → 登录 → 获取 JWT
  ├── 携带 JWT → 查看/修改个人信息、修改密码、上传头像或恢复默认头像
  ├── 携带 JWT → 获取初始上下文（用户+角色+权限+菜单）
  └── 管理员 → 用户列表、修改用户、删除用户、Ban/UnBan、强制下线
```

## 功能清单

| 功能 | 状态 | 说明 |
|---|---|---|
| JWT 验证 | ✅ | HS256 签名，Access Token 15min / Refresh Token 7天 |
| 验证码登录/注册 | ✅ | 6位数字图片验证码，Redis 5分钟过期，一次性消费 |
| 管理员-用户列表 | ✅ | 分页查询，脱敏返回 |
| 管理员-修改用户 | ✅ | 可改昵称/邮箱/角色/状态，不可改密码 |
| 管理员-删除用户 | ✅ | 软删除（GORM），不可删除自己和其他管理员 |
| 管理员-Ban/UnBan | ✅ | 一键翻转 status 状态 |
| 管理员-强制用户下线 | ✅ | 提升目标用户 token_version，让旧 Token 立即失效 |
| 普通用户-查自己信息 | ✅ | GET /api/user/info |
| 普通用户-修改自己信息 | ✅ | 只允许昵称和邮箱；出现 `avatar` 字段时明确拒绝 |
| 普通用户-修改头像 | ✅ | 静态 JPEG/PNG/WebP 完整解码并标准化为 JPEG/PNG |
| 普通用户-恢复默认头像 | ✅ | DELETE /api/user/avatar |
| 公开读取头像 | ✅ | 只输出可信标准化头像或内置默认 PNG |
| 普通用户-修改密码 | ✅ | 旧密码验证 + 两次新密码一致 + 复杂度校验 |
| 登出 | ✅ | Token 加入 Redis 黑名单，过期对齐 Token 有效期 |
| 个人中心-初始上下文 | ✅ | 返回用户信息 + 角色码 + 权限码 + 菜单树 |

## 数据模型设计

### model/user.go

```go
type User struct {
    gorm.Model
    Username               string
    Password               string
    Nickname               string
    Avatar                 string     // 旧头像兼容字段，新代码不再信任该 URL
    AvatarObjectName       string     // 服务端生成的可信头像对象名
    AvatarContentType      string     // image/jpeg 或 image/png
    AvatarContentSHA256    string     // 标准化头像输出的服务端 SHA-256
    AvatarValidationStatus string     // 可信头像必须为 validated
    AvatarValidatedAt      *time.Time
    Role                   string
    Status                 int
    TokenVersion           int
    Email                  string
}
```

`Avatar` 历史字段暂时保留用于兼容迁移，不提前删除。只有对象归属、UUID 文件名、扩展名、MIME 和验证状态全部可信时，DTO 才返回 `/api/avatars/<user-id>`；否则统一返回 `/api/avatars/default`。迁移期间不会读取、解码、删除或重写历史 MinIO 对象。

## DTO 设计

### dto/user.go

```go
// ========== 请求参数 ==========

type RegisterReq struct {
    Username    string `json:"username"  binding:"required,min=3,max=100"`
    Password    string `json:"password"  binding:"required,min=6,max=255"`
    Email       string `json:"email"     binding:"required,email"`
    Nickname    string `json:"nickname"`
    CaptchaID   string `json:"captcha_id"   binding:"required"`
    CaptchaCode string `json:"captcha_code" binding:"required,len=6"`
}

type LoginReq struct {
    Username    string `json:"username"     binding:"required"`
    Password    string `json:"password"     binding:"required"`
    CaptchaID   string `json:"captcha_id"   binding:"required"`
    CaptchaCode string `json:"captcha_code" binding:"required,len=6"`
}

// ========== 响应 ==========

type UserInfo struct {
    ID       uint   `json:"id"`
    Username string `json:"username"`
    Nickname string `json:"nickname"`
    Avatar   string `json:"avatar"`
    Email    string `json:"email"`
    Role     string `json:"role"`
    Status   int    `json:"status"`
}

type LoginResp struct {
    AccessToken  string   `json:"access_token"`
    RefreshToken string   `json:"refresh_token"`
    User         UserInfo `json:"user"`
}

// ========== 用户自改 ==========

type UpdateSelfReq struct {
    Nickname string `json:"nickname" binding:"max=100"`
    Email    string `json:"email" binding:"omitempty,email"`
}

type ChangePasswordReq struct {
    OldPassword     string `json:"old_password"     binding:"required"`
    NewPassword     string `json:"new_password"     binding:"required,min=6,max=255"`
    ConfirmPassword string `json:"confirm_password" binding:"required,min=6,max=255"`
}

// ========== 管理端 ==========

type UserListResp struct {
    List  []UserInfo `json:"list"`
    Total int64      `json:"total"`
    Page  int        `json:"page"`
    Size  int        `json:"size"`
}

type AdminUpdateUserReq struct {
    Nickname string `json:"nickname" binding:"max=100"`
    Email    string `json:"email"    binding:"email"`
    Role     string `json:"role"`
    Status   *int   `json:"status"`
}

// ========== 初始上下文 ==========

type InitialContextResp struct {
    User        UserInfo     `json:"user"`
    Roles       []string     `json:"roles"`
    Permissions []string     `json:"permissions"`
    Menus       []MenuDetail `json:"menus"`
}
```

实际 DTO 还会检测原始 JSON 中是否出现 `avatar`。即使值为空或 `null`，资料接口也会拒绝请求，避免客户端继续写入外部 URL 或 MinIO 路径。

## 接口设计

所有公开接口不需要认证，用户自操作接口需 JWT，管理员接口需 JWT + admin 角色。

### 1. 获取验证码

```http
GET /api/captcha
```

返回：

```json
{
  "code": 200,
  "data": {
    "captcha_id": "uuid-string",
    "captcha_img": "data:image/png;base64,..."
  }
}
```

说明：

- 6 位数字验证码，存入 Redis（key=`captcha:<id>`，5 分钟过期）
- 前端需将 `captcha_id` 随登录/注册请求一起提交

```http
Content-Type: application/json
```

Body：

```json

  "email": "newuser@example.com",
  "nickname": "新用户",
  "captcha_id": "uuid-string",
  "captcha_code": "385210"
```

```http
PUT /api/user/info
Content-Type: application/json
Authorization: Bearer <token>
```

Body：

```json
{
  "nickname": "新昵称",

```

说明：

- 只允许修改昵称和邮箱

- 不可修改用户名、角色、状态
- 请求中只要出现 `avatar` 字段就会返回稳定错误；头像只能使用专用上传或恢复默认接口修改

### 6. 修改密码

```http
PUT /api/user/password
Content-Type: application/json
Authorization: Bearer <token>
```

Body：

```json
{
  "old_password": "OldPass@123",
  "new_password": "NewPass@456",
  "confirm_password": "NewPass@456"
}
```

说明：

- 需验证旧密码正确
- 新密码与确认密码必须一致
- 新密码不能与旧密码相同
- 新密码需满足复杂度要求

### 7. 上传头像

```http
POST /api/user/avatar
Content-Type: multipart/form-data
Authorization: Bearer <token>
```

Body：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| file | file | 是 | 图片文件，上限来自 `file_upload.avatar_max_size_mb` |

约束：

- 必须且只能有一个名为 `file` 的文件 part
- 整个 multipart 请求体上限为 `file_upload.avatar_max_size_mb + 256 KiB`，额外空间只用于 multipart 边界和表单头
- 原文件 part 和重新编码输出均不得超过 `file_upload.avatar_max_size_mb`
- 只接受声明 MIME、真实类型和完整解码结果一致的静态 JPEG、PNG、WebP
- 动画 WebP、APNG、损坏图片、类型不一致图片会在写入对象存储前拒绝
- 输入任一边不得超过 8,192 像素，总像素不得超过 40,000,000
- 按比例缩放到最大 1,024×1,024，不放大小图
- 重新编码会移除 EXIF、定位、设备等非像素元数据
- 无透明通道输出质量 85 JPEG；有透明通道输出 PNG
- 输出仍受 `file_upload.avatar_max_size_mb` 限制
- SHA-256 在重新编码完成后计算，对应实际写入 MinIO 的 JPEG/PNG 字节，不对应原始上传图片
- 头像摘要不进入 object key、头像 URL、用户 DTO、普通日志或审计元数据，也不用于自动去重或恶意图片判定
- 私有 object key 由服务端生成，不返回客户端
- 新对象写入后，数据库明确确认未提交时会补偿删除新对象
- 数据库提交结果不确定时保留新对象且不清理旧对象，避免删除数据库可能已经引用的对象
- 新头像成功后才清理旧的可信系统头像；清理失败不回滚新头像

返回：

```json
{
  "code": 200,
  "msg": "头像上传成功",
  "data": {
    "id": 1,
    "username": "admin",
    "avatar": "/api/avatars/1"
  }
}
```

### 8. 恢复默认头像

```http
DELETE /api/user/avatar
Authorization: Bearer <token>
```

说明：

- 先清除数据库中的可信头像标识和 `avatar_content_sha256`，再尝试删除旧的系统头像对象
- 数据库更新失败时保留原可信头像记录和对象，并返回不泄露底层错误的持久化错误
- 已经处于默认头像状态时重复调用仍成功，不执行无变化更新或对象删除
- 旧对象清理失败不会回滚恢复默认结果
- 返回的用户信息中 `avatar` 为 `/api/avatars/default`

### 9. 公开读取头像

```http
GET /api/avatars/1
GET /api/avatars/default
```

说明：

- 两个接口均允许匿名只读访问，可直接用于普通 `<img src>`
- `/api/avatars/:user_id` 只输出服务端标准化的 JPEG/PNG
- 用户不存在、没有可信头像、只有历史外部 URL、对象缺失或存储暂时不可用时，统一返回内置默认 PNG
- 不请求、代理、重定向或显示历史外部头像 URL
- 响应不暴露 object key、MinIO 地址、头像摘要、验证元数据或用户资料
- 响应设置规范 `Content-Type`、`X-Content-Type-Options: nosniff` 和受控公开缓存头

### 10. 登出

```http
POST /api/user/logout
Authorization: Bearer <token>
```

说明：

- 将当前 Token 加入 Redis 黑名单（key=`blacklist:<token>`，过期时间对齐 Token 有效期）
- JWT 中间件每次请求检查黑名单

```http
PUT /api/admin/users/5/kick
Authorization: Bearer <admin_token>
```

Body：无

成功返回：

```json
{
  "code": 200,
  "msg": "强制下线成功"
}
```

说明：

- 接口不会删除用户，也不会禁用账号，只会提升目标用户的 `token_version`

- 不能强制下线其他管理员

- 新增该接口并重启服务后，`seed.Run` 会自动同步 API 表和权限码
- 手动调用 `POST /api/admin/apis/sync`、`POST /api/admin/apis/sync-permissions` 只用于调试或修复数据
- 普通管理角色需要拥有该接口生成的权限码才可调用；`admin` 角色可兜底访问

## 数据流

### 注册流程

```text
用户提交注册表单
  → 验证码校验（Redis captcha:<id>）
  → 密码复杂度校验
  → 用户名/邮箱查重
  → bcrypt 加密密码
  → 写入 users 表（role=user, status=1）
  → 返回用户信息（脱敏）
```

### 登录流程

```text
用户提交登录表单
  → 验证码校验
  → 锁定检查（Redis lock:<username>）
  → 查找用户（按 username）
  → 状态检查（status=1）
  → bcrypt 密码比对
    ├─ 失败 → incr 失败计数 → 检查是否触发锁定
    └─ 成功 → 清除失败记录
              → 查询 user_roles → roles
              → 查询 role_permissions → permissions
              → 查询 role_menus → menus（初始上下文时）
              → 签发 JWT（含 userID + roles + permissions）
```

### 初始上下文数据流

```text
前端加载完成
  → GET /api/user/context
  → JWT 中间件注入 userID、roles、permissions 到 Gin Context
  → 查询用户信息
  → 查询用户菜单树（user → user_roles → role_menus → menus → 组装树）
  → 组装返回
```

## 密码规则

- 最少 6 位
- 必须包含大写字母、小写字母、数字、特殊符号中至少 3 种

```go
func validatePassword(pw string) error {
    // 长度检查
    // 字符类型统计（upper, lower, digit, special）
    // 至少满足 3 种
}
```

## 安全约束

| 约束 | 说明 |
|---|---|
| 管理员不能操作自己 | DeleteUserByAdmin / UpdateUserByAdmin / ToggleUserStatus 均校验 |
| 管理员不能操作其他管理员 | 检查目标用户 role != "admin" |
| 管理员数据范围限制 | 用户列表、修改、删除、Ban/UnBan、强制下线都会校验目标用户是否在当前管理员数据范围内 |
| 密码永不明文存储 | bcrypt 加密，即使数据库泄露也无法还原 |
| Token 黑名单 | 登出后 Token 加入 Redis 黑名单，过期时间对齐 Token 有效期 |
| Token 实时失效 | 修改密码、权限变更、强制下线等操作会提升 token_version，让旧 Token 失效 |
| 验证码一次性消费 | 校验后立即删除（无论成功失败），防止重复提交和暴力穷举 |
| 邮箱唯一性 | 注册和修改均校验（排除自己） |
| 头像写入收口 | 资料接口拒绝 `avatar`；头像只能通过专用上传或恢复默认接口修改 |
| 历史头像隔离 | 旧 `avatar` URL 不再作为可信资源，不请求、不代理、不重定向 |
| 头像标准化 | 只保存重新编码后的 JPEG/PNG，私有 object key 不进入 API DTO |
| 头像完整性基线 | 对标准化输出计算 SHA-256 并与可信元数据同次保存；摘要不对外暴露且不承担病毒检测或去重职责 |

## Apifox 测试顺序

1. 获取验证码（GET /api/captcha）
2. 注册新用户（POST /api/register）
3. 获取验证码 → 登录（POST /api/login），拿到 access_token
4. 查个人信息（GET /api/user/info）
5. 修改昵称或邮箱（PUT /api/user/info）
6. 在资料请求中加入 `avatar`，确认被明确拒绝且数据库不写入客户端 URL
7. 上传合法静态 JPEG/PNG/WebP（POST /api/user/avatar），确认返回 `/api/avatars/<id>`
8. 上传多文件、空文件、超限、损坏、动画或 MIME 不一致图片，确认稳定 `error_code`
9. 不携带 JWT 读取 `/api/avatars/<id>`，确认返回 JPEG/PNG；读取 `/api/avatars/default`，确认返回默认 PNG
10. 恢复默认头像（DELETE /api/user/avatar），再次读取用户信息确认返回默认地址
11. 修改密码（PUT /api/user/password）
12. 获取初始上下文（GET /api/user/context），确认头像地址与个人信息一致
13. 管理员登录 → 查用户列表（GET /api/admin/users），确认头像 DTO 不暴露对象存储信息
14. 管理员修改用户（PUT /api/admin/users/:id）
15. 管理员 Ban/UnBan（PUT /api/admin/users/:id/status）
16. 管理员强制用户下线（PUT /api/admin/users/:id/kick）
17. 用被强制下线用户的旧 Token 访问 → 验证返回 401
18. 管理员删除用户（DELETE /api/admin/users/:id）
19. 登出（POST /api/user/logout）
20. 用已登出的 Token 访问 → 验证黑名单生效

## 注意事项

- `UserInfo` 返回不包含 `Password` 字段，确保密码永不到达前端
- 前端只使用 `/api/avatars/<user-id>` 或 `/api/avatars/default`，不得拼接历史 MinIO URL
- 头像由应用接收、验证、重新编码后写入私有 `image` bucket，不是客户端直传
- 历史 `Avatar` 字段暂时保留兼容，但新代码不把它作为可信资源
- `InitialContext` 接口中的 `roles` 和 `permissions` 从 JWT context 读取，不在接口内重复查库
- 管理员操作均有双重保护：不能操作自己 + 不能操作其他管理员
- 管理员操作用户时还会叠加数据权限校验，不能操作数据范围外的用户
- 软删除用户后，其关联的 user_roles 不自动清理（保留历史关系）
- 密码修改、强制下线、权限相关变更都会让旧 Token 失效

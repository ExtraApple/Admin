- 当前行为以 `openspec/specs/file-management/spec.md` 和 `openspec/specs/user-management/spec.md` 为准。
- 本轮收敛 change 保留在 `openspec/changes/archive/2026-07-23-refine-upload-security-policy/`；原始加固 change 保留在 `openspec/changes/archive/2026-07-16-harden-file-upload-security/`。

本文只记录改造背景、实施概要、版本边界和后续优化方向，不重复复制 OpenSpec 中的完整接口行为、状态矩阵和验收场景。

## 改造背景

改造前，管理员普通文件上传和用户头像上传主要依赖文件大小、客户端文件名、扩展名及声明 MIME，无法可靠阻止伪装文件、损坏内容、超大 multipart 请求和外部头像 URL。

V1 的目标是在不引入外部恶意文件扫描服务的前提下，为两类上传建立一致、可审计、可迁移且可自动化测试的格式策略安全边界。

## V1 实施概要

V1 已同时加固以下入口：

- 管理员普通文件上传：`POST /api/admin/files`
- 用户头像上传：`POST /api/user/avatar`

主要成果：

- 在 multipart 解析前限制请求体，并严格限制为单个名为 `file` 的文件 part。
- 使用服务端生成的 object key，清洗展示文件名，不信任客户端路径、扩展名或声明 MIME。
- 管理员普通文件采用严格类型白名单和内容验证，只允许 PDF、UTF-8 TXT、UTF-8 CSV。
- 头像完整解码后移除元数据、限制尺寸并重新编码为标准 JPEG 或 PNG。
- 文件记录增加验证状态、检测 MIME、策略版本、验证时间、服务端 SHA-256 和稳定失败原因。
- 头像对标准化重新编码后的实际存储字节计算 SHA-256，并与可信头像元数据同次保存。
- 历史文件和头像只回填验证状态；迁移期间不读取、解码、删除或重写历史 MinIO 对象。
- 管理员文件只通过应用接口受控附件下载；预览兼容路由统一返回 HTTP 409。头像读取继续使用独立受控接口。
- 上传成功、策略拒绝和可安全分类的失败会记录结构化审计元数据，但不记录文件内容、object key、签名 URL、存储凭据或底层解析错误。
- 配置项写入 `config.yaml`，非法值会导致服务启动失败。

V1 管理员普通文件只允许 PDF、UTF-8 TXT 和 UTF-8 CSV。JPEG、PNG、WebP 只允许进入用户头像链路。所有 Office 文档当前均不受支持。

SHA-256 只作为实际存储内容的完整性比较基线：不信任客户端摘要，不用作 object key、唯一约束、自动去重或恶意文件判定，也不进入普通日志、审计元数据或访问 URL。格式验证和内容摘要均不表示已经完成病毒或恶意内容扫描。

## V1 边界

V1 不包含：

- 外部恶意文件扫描或病毒查杀。
- 通用压缩包、所有 Office 文档、脚本和可执行文件上传。
- 管理员普通文件图片上传和内联预览。
- CSV 或 Excel 业务数据导入。
- 多文件或批量上传。
- 上传限流和用户存储配额。
- 启动时批量扫描历史 MinIO 对象。

新增文件类型不能只通过修改配置开放，必须经过需求、风险、OpenSpec 和自动化测试评审。

## V2 及后续优化

以下能力只是 V2 或更后续版本的候选方向，不构成必须实现的版本承诺，也不会在 V1 中隐式开启：

1. **ClamAV 或外部恶意文件扫描**
   - 评估 ClamAV、ICAP 或云扫描服务。
   - 明确扫描超时、不可用、误报、重试和 fail-open/fail-closed 策略。
   - 增加扫描状态、签名库版本、监控和告警，但不记录文件内容。
2. **隔离区**
   - 未扫描、扫描中、可疑和确认恶意文件进入不可下载、不可预览的隔离存储。
   - 设计管理员复核、释放、删除和审计流程。
3. **批量重新验证**
   - 为历史文件提供可续跑、可限速、可重试、可观测的后台任务。
   - 单个对象失败不得阻断整个批次，且不得在迁移或服务启动期间同步扫描。
4. **上传限流**
   - 按用户、IP、接口或租户限制请求频率和并发数。
   - 对超限结果使用稳定错误码并纳入监控。
5. **存储配额**
   - 按用户、组织或租户限制文件数量和累计容量。
   - 明确上传、删除、轮转、补偿失败和孤立对象对配额的影响。
6. **批量上传**
   - 在单文件 V1 稳定后再设计批量请求、部分失败、幂等和逐文件审计语义。
   - 每个文件仍必须独立通过完整安全策略，不能以批次结果绕过验证。
7. **新增文件类型评审**
   - 每种新增类型先建立 GitHub Issue 和独立 OpenSpec change。
   - 明确业务用途、扩展名/MIME/内容验证、下载与预览策略、危险样本和回归测试。
   - Office 文件不预设为 V2 必做能力；只有出现明确业务需求时，才重新选择格式、验证方案和访问策略。
   - 压缩包、脚本和可执行文件默认继续拒绝；只有具备隔离、扫描和审计方案后才重新评估。
8. **主动完整性检查**
   - 在明确运维需求后，再设计受控回读、摘要比较、异常状态和告警流程。
   - 不在服务启动时批量扫描 MinIO，也不把当前 SHA-256 基线误当作持续完整性证明。

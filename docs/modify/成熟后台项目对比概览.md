## 与成熟项目的主要差距

### 1. 自动化 API 文档已补基础能力

当前已经新增基于 Gin 路由和 `apis` 表元数据的 OpenAPI 文档生成能力：

```text
GET /docs
GET /docs/openapi.json
```

手写 `docs` 继续保留，用来写模块说明、测试流程和设计约定；OpenAPI JSON 用于 Apifox 导入和接口路径同步。

后续还可以继续补强：

- 响应 DTO Schema。
- 错误码枚举。
- 字段示例。
- 更细的接口描述。

### 2. Seed 测试基础已完成，数据库迁移延后实施

当前已经补上 Go 代码版 Seed 基础化，能够在启动时幂等补齐默认角色、权限分组、字典、API 元数据、权限码、菜单、admin 授权和超级管理员账号。

目前还已经使用纯 Go SQLite 内存数据库完成 Seed 基础测试，覆盖：

- 空库初始化。
- 重复执行幂等性。
- 缺失权限和菜单关系补齐。
- 软删除默认菜单恢复。
- 用户修改过的菜单字段不被覆盖。

当前阶段继续使用：

```text
生产数据库：MySQL
表结构同步：GORM AutoMigrate
基础数据初始化：seed.Run
Seed 自动测试：SQLite 内存数据库
```

数据库 migration 不作为当前紧接着实施的模块。项目仍在快速增加基础功能和调整数据结构，如果现在过早维护大量迁移脚本，会产生较高的脚本修改和测试成本。

完成主要基础功能、核心表结构趋于稳定后，再增加：

- `migrations` 数据库迁移目录。
- `goose` 或 `golang-migrate` 等正式 migration 工具。
- Seed 版本记录。
- 默认数据变更策略。

该阶段的目标是让正式环境的版本升级可以被追踪、回滚和验证，逐步替代生产环境只依赖 `AutoMigrate` 的方式。

数据库支持建议分层推进：

```text
当前阶段：MySQL + AutoMigrate + Go Seed
测试阶段：SQLite 内存库验证 AutoMigrate + seed.Run
基础功能稳定后：migrations + migration 工具
长期扩展阶段：PostgreSQL 驱动适配和 psql 集成验证
```

PostgreSQL 和 `psql` 暂时不进入近期开发优先级。`psql` 是 PostgreSQL 的命令行客户端，适合在项目正式支持 PostgreSQL 后，用于执行迁移、检查表结构和进行集成测试，不适合作为当前 MySQL 主路径下的 Seed 测试工具。

未来确实需要 PostgreSQL 时，再先减少 MySQL 方言绑定，例如：

- 把 `initialize/mysql.go` 抽象为通用 `initialize/database.go`。
- 将配置从 `mysql:` 逐步抽象为 `database.driver`。
- 增加 `gorm.io/driver/postgres`。
- 清理 MySQL 风格 SQL，例如反引号字段引用。
- 避免使用 `group` 这类数据库关键字作为真实列名。
- 检查 model tag 中的 `tinyint`、`varchar` 等方言类型。

SQLite 不作为正式生产数据库主路径，只用于快速自动测试。当前已经使用 `:memory:` 验证：

- 空库 `AutoMigrate` 是否能成功。
- `seed.Run` 是否能重复执行。
- 默认角色、权限、菜单、API、字典是否能补齐。
- admin 角色权限和菜单绑定是否幂等。
- 新增模块后是否破坏基础初始化链路。

这样可以在不依赖本地 MySQL 服务的情况下快速运行初始化测试。等 migration 工具落地后，再补 MySQL 迁移集成测试；PostgreSQL 集成测试和 `psql` 验证放到多数据库支持阶段。

### 3. 权限引擎需要进一步抽象

当前项目已经实现了 API 动态权限中间件，这是正确方向。

但成熟后台项目中，权限判断通常会抽象成统一能力，例如：

```text
PermissionChecker
RoleChecker
DataScopeChecker
```

这样后续如果想接入 Casbin，或者调整 RBAC 模型，不需要大面积修改业务代码。

短期不一定要立刻换 Casbin，但建议把权限判断逻辑保持独立，不要散落在 handler 或 service 中。

### 4. 测试体系不足

当前模块已经很多，如果没有测试，后续改动权限、菜单、API、组织、日志时很容易互相影响。

建议优先补这些测试：

- 登录 / 注册 / JWT 鉴权测试。
- API 动态权限拦截测试。
- 角色绑定权限测试。
- 菜单绑定 API 测试。
- 组织数据范围测试。
- 文件上传安全测试。
- 审计日志记录测试。

优先使用：

```text
net/http/httptest
testing
test database
```

### 5. 文件上传安全策略需要补齐

当前文件管理已经支持上传、下载、列表、详情、删除、轮转等能力。

但安全策略仍需要补充：

- 文件大小限制。
- MIME 白名单。
- 危险扩展名拒绝。
- 文件名清洗。
- 图片类型二次校验。
- object key 防路径穿越。
- 预签名链接过期时间配置。

这个属于安全风险点，优先级较高。详细策略见[文件上传安全优化建议](文件上传安全优化建议.md)。

### 6. 运行状态和监控不足

当前已经有 Zap 和审计日志，但还缺少系统运行层面的可观测能力。

建议补充：

- `request_id` 请求追踪。
- 健康检查接口。
- MySQL 状态检查。
- Redis 状态检查。
- MinIO 状态检查。
- 基础 metrics。
- 慢请求记录。
- 异常请求统计。

这些能力会让后台更容易排查线上问题。

### 7. 代码生成能力不足

当前已经有很多类似 CRUD 模块：

- 字典管理
- 组织管理
- API 管理
- 菜单管理
- 角色管理

这类模块结构高度相似，后续可以考虑做一个内部代码生成器，自动生成：

```text
model
dto
service
handler
router
docs
```

成熟项目通常会有 AutoCode 或代码生成工具，这能减少重复劳动。

## 适合后续补充的模块

### 1. 首页仪表盘

建议展示：

- 用户总数。
- 今日新增用户。
- 今日登录次数。
- 今日操作日志数量。
- 文件上传数量。
- 最近异常登录。
- 最近管理员操作。
- 系统存储占用。

这是后台管理系统的第一屏，能明显提升完整度。

### 2. 内部消息 / 通知公告

TODO 中已经保留该模块。

建议功能：

- 发送站内消息。
- 消息收件箱。
- 消息分类管理。
- 标记已读。
- 撤销消息。
- 删除消息。

这类功能在真实后台中很常用。

### 3. 岗位管理

当前已经有组织管理，但还没有岗位概念。

组织表示用户属于哪里，岗位表示用户在组织里担任什么职责。

例如：

```text
技术部
  - 后端工程师
  - 前端工程师
  - 测试工程师
```

岗位可以和用户、组织、角色形成更完整的管理关系。

### 4. 数据导入导出

建议后续支持 Excel 导入导出：

- 用户导出。
- 日志导出。
- 组织成员导出。
- 文件记录导出。
- 字典导入导出。

后台用户会非常依赖这个能力。

### 5. 配置管理增强

当前有 `config.yaml`，但还可以继续扩展：

- 后台可视化配置。
- 敏感配置脱敏。
- 配置变更日志。
- 部分配置热更新。

不建议一开始把所有配置都做成动态配置，优先处理业务开关类配置。

## 当前阶段判断

当前项目不建议急着上微服务。

更适合先补齐后台系统底盘：

- 文件安全。
- 核心链路测试。
- 请求追踪、健康检查和运行监控。
- 权限抽象。
- 自动文档响应模型。
- 数据导出。

自动文档基础、初始化数据和 SQLite Seed 测试已经完成，当前应维护而不是重复建设。完成剩余底盘能力和主要业务模块后，再进入 migration 工具化和多数据库适配阶段。

成熟项目和当前项目最大的差距，不是模块数量，而是工程化可靠性。

如果这些底盘补齐，后续无论继续做单体，还是拆分微服务，都会更稳。

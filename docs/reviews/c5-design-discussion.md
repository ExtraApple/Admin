## 3. 范围与非目标

### 3.1 已选范围

- 三个能力全部纳入 C5，不拆开只做公告或只做图片。
- 复用 `messaging-cleanup`，不建立第二套调度框架。
- 公告以组织副本为处理单位；文件清理生命周期由 `internal/files` 负责。
- 新增对象清理队列及其自动重试，解决对象删除失败后无法再次定位的问题。
- 补充配置校验、迁移登记、受控日志及未来运行手册说明。

### 3.2 明确不做

- 不新增人工触发 HTTP API、权限码、管理前端、dry-run 模式或专用运维命令。
- 不新增 C5 总开关或三类任务独立开关。
- 不新增公告失败任务表、公告 publish_failed 状态或调度专用事件。
- 不新增 Redis／数据库分布式锁、清理租约、processing 状态或独立 cleanup 模块。
- 不新增任务运行历史表；不为成功清理记录建立归档任务。
- 不扩展 Outbox dead 恢复控制面；不修改其他有意保留接缝。

这些非目标不等于可以省略事务和并发正确性。若无法在已选边界内满足安全约束，应先说明冲突，不暗中引入新状态或接受数据丢失。

## 4. 调度、配置与首次运行

### 4.1 已选调度模型

- 应用启动后立即运行一轮，后续按一小时周期执行。
- 同一进程内单 goroutine 顺序运行，不重叠开启下一轮。
- C5 三个子任务顺序固定：图片清理 → 公告发布 → 公告过期。
- 一个子任务失败不阻止后续任务；进程退出或父 context 已取消时安全停止。
- 组合根每轮生成统一 UTC `now`，显式传入三个任务作为本轮资格判断时间，不依靠各任务分别取零值兜底时间。
- 整轮固定 15 分钟总超时；三个 C5 子任务分别固定 5 分钟超时，不增加超时配置、不转让子任务时间预算。
- 超时不回滚此前已提交的事务；未完成工作留给后续轮次。调用链必须响应 context 取消。
- 保留现有受众快照清理、终态 Consumer 死信清理；其执行位置及超时预算尚需核对，不能以接入 C5 为由删除。

**时间边界说明**：现有实现是本轮结束后再等待一小时，并非每个整点触发。是否严格沿用这一 fixed-delay 语义，以及 15 分钟总超时如何容纳原有两项清理，见第 10 节；不能将其写成精确的一小时服务时限。

### 4.2 最终配置选择

```yaml
messaging:
  cleanup_batch_size: 100
```

- 唯一新增批量配置，默认 100，允许 1–1000。
- 原始配置为 0 时按未配置填默认 100，不能用 0 关闭 C5。
- 负数或大于 1000 在配置加载阶段拒绝，不静默回退。
- 配置启动时读取，任务使用已校验的正数，不新增后台重复配置校验。
- 同一值控制单次查询上限及每类任务的单轮工作量上限。
- 图片清理、公告发布、公告过期各自独立计额，不共用一个总预算。
- 默认三类 C5 任务合计最多约 300 个处理单位；这不是数据库 SQL 次数或对象存储请求次数上限，也未包含原有 cleanup 工作。
- 新图片登记与清理队列重试如何分配图片任务预算尚未确定，不能额外默认为重试再给 100 条。

### 4.3 读取顺序与计额

- 公告和首次图片候选按 `id ASC`，采用 `id > last_id` 游标思路；下一轮从头查找符合条件的记录。
- 上限控制工作量，不以成功数作为停止条件。冲突、失败等已进入处理流程的记录仍消耗预算。
- 图片候选应为消息图片、未绑定、绑定期限已过，已有 pending/dead 清理记录不重复登记。
- 最终单轮上限等于查询上限后，通常只需一页；不再有“每页 100、每轮 1000”的有效配置。
- 从头读取的饥饿风险、过滤发生在数据库还是应用层、队列重试分页方式尚待核实，见第 10 节。

### 4.4 首次启用

允许立即处理已有到期数据，不设置部署时间水位，不跳过历史记录。

部署前应核对真实环境中的 scheduled 公告、已到期 published 公告、未绑定过期图片及关联存储范围。控制手段为批量上限、超时、事务隔离和日志，不新增 dry-run 或人工确认开关。该检查应写入后续 runbook，而不是假定本机历史零数据适用于部署环境。

## 5. 公告生命周期与消息投递

### 5.1 副本级处理

- 每个组织副本独立查询、独立事务、独立 CAS。
- 一个副本失败不回滚其他组织副本，不按 logical_id 合并事务或事件。
- 发布仍经现有 `ChangeMessage` 产生 `MessagePublished`，过期产生 `MessageExpired`。
- 沿用既有 Outbox／Consumer 投递和刷新语义，不只修改状态，不新建投递阶段或专用事件。
- 公告状态与其事件写入应保持既有数据库事务一致性；C5 不等待 RabbitMQ 确认。
- CAS 冲突跳过本条；其他数据库或状态转换失败记录后继续，下轮重新查询仍符合条件的副本。
- CAS 冲突不等于必然被另一个发布任务成功处理，也可能来自编辑、撤销等并发操作；不能凭冲突计为发布成功。
- 公告不增加独立失败表，Outbox dead 不回滚公告为 scheduled，也不自动产生第二个发布事件。

### 5.2 RabbitMQ 最后讨论口径

| 启动时配置 | 运行时连接 | 图片清理 | 公告过期 | 公告发布 |
| --- | --- | --- | --- | --- |
| 未配置 | 不适用 | 执行 | 执行并沿用事件路径 | 跳过，记录原因 |
| 已配置 | 正常 | 执行 | 执行 | 执行，写 Outbox |
| 已配置 | 暂时故障 | 执行 | 执行 | 继续写 Outbox，由现有 worker 处理 |

- 配置只在启动时读取；从未配置改为已配置需重启，不热创建 publisher。
- 已配置后的连接恢复沿用现有连接设施，不等同于禁止网络重连。
- 发布跳过每轮只记一条汇总，原因 `rabbitmq_not_configured`，不额外查询待发布数量，不逐条刷日志，不计为失败。
- 允许 published 与事件投递失败并存，不因 broker 故障回滚业务状态。
- Outbox／Consumer 与 C5 独立并发运行，C5 不编排或等待它们。
- Outbox dead 人工恢复不纳入 C5；后续 runbook 应引用经验证的现有入口。如没有入口，必须如实写明，不能虚构。

**证据校正**：`outbox_worker.go:110-123` 按失败次数递增，在第 5 次发布失败时进入 dead；非 dead 才设置下一次重试时间。访谈所述“五段延迟 1/2/4/8/16 秒全部执行后才 dead”不能直接作为事实；实际配置值和具体调用次序应核对。未配置 broker 时 worker 不注册，与已注册 worker 执行失败进入 dead 是两种不同情况。

**决策出处限制**：未配置 RabbitMQ 时跳过发布，是访谈后半段沿用并反复确认的口径；最初从“全部不门控”切换时，助手曾在没有对应新选项的情况下解释用户的 `1`。正式 OpenSpec 定稿前应明确复核这一实质变更，不能把它解释成由 Outbox 代码唯一推导出的必要行为。

## 6. 消息图片清理队列

### 6.1 所有权与最终流程方向

`internal/files` 负责图片到期候选、清理记录、对象删除、重试、读取阻断和轮转排除。Messaging 不直接访问清理表，不引入第三个业务模块。组合根编排服务调用；具体跨模块接口尚未定稿。

最后讨论采用的流程为：

1. 查询到期、未绑定且尚未登记的消息图片。
2. 逐个对象开启短数据库事务，重新确认清理资格，登记唯一 pending 清理记录，提交。
3. 登记失败则保留 File Record，不执行该对象的存储删除，记录错误并继续其他对象。
4. 事务提交后执行对象删除，数据库事务不跨对象存储调用。
5. 所有应清理位置均成功删除或确认不存在后，在新事务中条件删除 File Record 与队列记录。
6. 删除失败保留 File Record 与队列记录，更新稳定错误码和重试调度字段。
7. 队列记录存在期间拒绝对应消息图片读取，且轮转不应再选择该对象。

这是已选目标，不是“唯一可靠实现”。对话曾错误声称保留 File Record 是可靠重试的必需条件；实际上队列完整保存定位信息、并与删除 File Record 原子提交，也可构成另一种可靠设计。本文记录用户后来围绕“保留 File Record、队列阻断读取”继续选择的方向，不重开旧选项，也不将错误理由保留为架构依据。

### 6.2 拟定持久化模型

暂用讨论名 `message_image_cleanup_failures`。由于它在首次对象删除前就登记，实际承载的是清理工作队列，而非“仅失败后新增”的事件流水；正式命名需与职责核对。

| 字段 | 讨论确定的用途 |
| --- | --- |
| `bucket`、`object_name` | 完整、冻结的原始对象定位信息 |
| `object_key_hash` | SHA-256 去重键，唯一索引 |
| `status` | pending 或 dead |
| `retry_count` | 已执行的重试次数 |
| `next_retry_at` | 下一次允许重试时间 |
| `last_error_code` | 稳定错误分类，不存原始错误文本 |
| `created_at`、`updated_at` | 生命周期时间 |

- 日志及条件删除还需要稳定的清理记录 ID／File Record 关联；其具体字段、关联约束和索引未完成技术设计。
- hash 输入拟为 `bucket + "\x00" + object_name`；完整路径仍保存，不能只保存 hash。
- 不截断对象路径，不使用长字符串前缀索引作为完整路径唯一性的替代。
- hash 唯一键冲突时核对完整路径：同一路径去重；不同路径拒绝登记、保留原 File Record、告警，不覆盖、不加冲突序号。
- 同对象已有 pending 或 dead 记录均不重新登记、不重置失败次数。
- 复用现有启动自动迁移机制登记新模型，验证表和唯一索引幂等；不修改 File Record 表新增清理状态字段。
- 具体字段类型、对象名上限、MySQL 唯一索引形式及迁移入口仍待核对，不能直接把讨论中的示例长度当成 DDL。

### 6.3 重试与人工处理

- 对象存储删除在业务语义上幂等；已不存在按成功处理。
- 每小时重试，最多 24 次，使用 `next_retry_at` 控制资格；不是指数退避或无限重试。
- 达到上限转 dead，停止自动重试并告警，不新增 processing、completed 状态。
- 成功后物理删除清理记录；不长期保存成功流水，不新增成功记录保留任务。
- dead 记录保留供人工核查，不自动过期，不新增 HTTP 或命令入口。
- 人工确认各目标对象已清除后，应按最终一致性规则处理 File Record 与队列记录；不能只删队列让仍保留的 File Record 再次入队。
- 初次删除尝试是否计入“24 次”、第 24 次还是超过 24 次转 dead，访谈文字有差异，须统一后形成测试边界。
- 多实例允许重复发现、幂等删除，使用唯一键和条件更新，不引入租约或分布式锁。唯一键本身不保证重试次数只加一次，详见第 10 节。

## 7. 对象路径、轮转与 bucket 配置

### 7.1 已选方向

- 登记时冻结原始 bucket 和 object_name，后续不随 File Record 轮转改写。
- 轮转候选查询以 `NOT EXISTS` 或等价条件排除 pending/dead 队列对象；由 files Repository 统一维护。
- 不把轮转工作转移给清理队列，不新增 File Record 状态字段。
- 接受多实例和查询后并发处理，不使用跨任务分布式锁。
- 原始位置之外，讨论选择检查当前文件配置中的受支持热桶、冷桶；不硬编码默认名称，不新增 cleanup_buckets。
- 当前配置的非空、已启用 bucket 去重后参与检查；未启用或为空的冷桶跳过。
- 同一对象在多个受支持位置存在时，选择清理全部对应副本；任一位置失败保留队列。
- 历史队列继续按冻结的原始 bucket 重试，即使原始 bucket 已不在当前配置中。不推测其他历史 bucket，不扫描任意桶。
- 历史原始 bucket 必须来自本应用受信登记路径；无法确认归属时交由人工，存储不可访问则按既定重试上限处理。

### 7.2 不能据此宣称竞态已解决

按旧路径查到“对象不存在”，不证明对象没有被移到冷桶。即使检查热冷两个桶，轮转仍可能在检查结束后完成复制，形成新孤儿对象。

同样，当前配置提供 bucket 名称只说明位置受配置管理，**不能证明不同 bucket 的同名对象属于同一 File Record**。访谈选择批量清理对应副本时附带了“必须证明归属”的前提；在证明前不得直接执行跨桶同名对象删除。配置键名、轮转 Copy/Delete 顺序、路径唯一性以及未启用冷桶的既存对象风险须继续核实。

## 8. 运行观测与错误边界

### 8.1 记录方式

- 只写结构化日志，不新增运行历史表。
- 沿用现有 `RuntimeLogger`、`RuntimeLogField` 和 App 适配边界，不新增日志库，不直接绕过白名单写 zap。
- 每轮生成 UUID `run_id`；复用现有 `messaging-<UUID>` 的 `worker_id`，不另建 cleanup worker ID 或配置。
- 每轮及子任务开始、结束有记录；成功对象不逐条刷日志，失败对象逐条记录，dead 和登记失败重点告警。
- 日志只含稳定记录 ID、任务信息、计数、稳定错误码等，不记录 bucket、object_name、主机名、IP、凭据或原始基础设施错误。
- 完整对象定位只在受控队列／文件记录中保存。队列登记失败可能没有队列 ID，应以 File Record ID 定位。

### 8.2 拟定事件与字段

| 固定事件名 | 用途 |
| --- | --- |
| `messaging_cleanup_started` | 轮次开始 |
| `messaging_cleanup_finished` | 轮次汇总 |
| `messaging_cleanup_task_started` | 子任务开始 |
| `messaging_cleanup_task_finished` | 子任务汇总 |
| `messaging_cleanup_item_failed` | 单条失败 |
| `messaging_cleanup_task_skipped` | 配置／父 context 导致未执行 |
| `messaging_cleanup_dead_lettered` | 清理队列转 dead，不等于 Consumer 死信 |

拟定公共字段：`run_id`、`worker_id`、`task`、`stage`、`status`、`failure_code`、`processed`、`succeeded`、`skipped`、`failed`、`duration_ms`、`timed_out`，以及相关记录 ID、重试次数、批量值和轮次时间。

任务标识为 `message_image_cleanup`、`publish_due_announcements`、`expire_due_announcements`。

- status=succeeded：正常完成。
- status=failed：已执行但发生处理错误。
- status=timed_out：子任务超时。
- status=skipped：因未配置 RabbitMQ 或父 context 取消而未执行；计数为 0。
- processed 按实际尝试的对象／公告副本计，不按逻辑公告合并；失败或冲突同样计工作量。
- 单条 CAS 冲突、已有队列记录等可记 skipped。访谈也将对象不存在放进 skipped，但又将其定义为成功终结；该统计冲突须在落地时统一，不能重复计数。

**现有白名单限制**：`internal/app/messaging.go:282-288` 目前会丢弃未列入白名单的字段；run_id、task 和新计数字段不能仅在调用处传入就宣称已输出。日志白名单及其文档需同步，且 files 不应为日志而反向依赖 messaging 业务模块。

### 8.3 拟定后台稳定运行码

- 公告：`announcement_dependency_unavailable`、`announcement_state_conflict`、`announcement_persistence_failed`。
- 图片：`message_image_cleanup_dependency_unavailable`、`message_image_cleanup_persistence_failed`、`message_image_cleanup_storage_unavailable`、`message_image_cleanup_permission_denied`、`message_image_cleanup_object_not_found`。
- 队列：`message_image_cleanup_failure_record_failed`、`message_image_cleanup_hash_collision`。
- 配置跳过原因：`rabbitmq_not_configured`。

运行码不加入对外 HTTP 错误码目录，不持久化原始错误文本。object_not_found 是幂等结果，不作为失败重试。拟定码能否由现有错误分类可靠产生须核实，不能只声明常量而没有实际分类路径。

## 9. 被替代方案与对话纠正

| 早期说法 | 最后讨论方向／纠正 |
| --- | --- |
| 先删 File Record，失败后才补写失败记录，补写失败依赖日志兜底 | 已放弃这一丢补偿记录窗口；先持久化队列，保留 File Record，存储成功后一起清理 |
| 保留 File Record 是可靠队列的唯一实现 | 不成立；只是本次后续选择采用的方向，不能作为唯一可行性的论据 |
| 每页 100、每轮 1000，两个批量配置 | 已被单一 cleanup_batch_size 替代，默认每类每轮 100 |
| 三类任务完全不受 RabbitMQ 配置门控 | 后半段改为仅自动发布受启动配置门控，须核实决策出处限制 |
| Broker 恢复后所有失败 Outbox 都会自动继续投递 | 不成立；需区分未领取 pending 与有限失败后 dead，后者恢复入口待核实 |
| 失败后记录对象路径／原始错误方便人工清理 | 最后选择仅稳定 ID 和错误码进入日志；完整定位留在数据库 |
| 直接以 bucket/object_name 长字符串唯一索引去重 | 最后选择 SHA-256 唯一键，并核对完整路径冲突 |
| 旧路径不存在即代表所有存储对象已清除 | 已扩展到受支持位置核实，但轮转竞态仍未证明消除 |
| 消息模块决定哪些图片到期 | 清理资格和文件生命周期应由 files 负责，Messaging 不直接操作表 |
| 人工完成后可标记 completed | 最终无 completed 状态，应按最终一致性规则删除记录 |
| CAS 冲突必然表示别人已成功发布 | 不成立；只能说明当前版本无法提交，需重新读取实际状态 |

## 10. 技术核对与待裁决清单

下列项目不改变用户已选目标，也不宣称是新发现的现网缺陷；它们是将讨论变成可实施设计之前必须补齐的证据与边界。

| 项目 | 未闭合点 | 下一步核对／决策 |
| --- | --- | --- |
| 周期与吞吐 | 现有循环为完成后等一小时；有限额时积压延迟可超过一小时 | 明确 fixed-delay 是否沿用，不承诺整点发布或最大一小时延迟 |
| 到期发布与过期相遇 | 启动时某 scheduled 公告可能已超过 expires_at；当前顺序先发布再过期 | 核对状态机、读过滤与消费语义，决定是否允许对已失效公告补发事件 |
| 失败记录饥饿 | 每轮从头且最多 100 条，前 100 条永久失败时后续记录可能永远进不来 | 证明后续合格记录有推进机会；不把主键排序当成公平性证明 |
| 图片预算 | 首次登记与到期重试共属图片任务，但预算分配、排序未定 | 定义预算分配及一次对象尝试的计额，避免重复处理同对象 |
| 重试上限 | 初次尝试与 24 次重试口径不一致；多实例可能同时失败并多次加计数 | 明确边界及条件更新；唯一 hash 不能代替重试次数并发控制 |
| 绑定与登记并发 | 现有绑定以请求时间和条件更新判定；清理扫描到提交存在窗口 | 核对读取、绑定、登记和删除全路径，不能误清理已绑定图片 |
| 轮转与跨桶删除 | 排除查询不能阻止已查出的对象继续移动；同名不证明同归属 | 核对实际 Move 和命名约束，证明删除范围及检查后竞态，否则先裁决 |
| bucket 配置与历史 | 关闭轮转不代表冷桶无对象；历史队列仅冻结一个原始 bucket | 核对真实配置键、历史范围与可信来源，不能用猜测桶名兜底 |
| 并发幂等终结 | 一个实例成功后，另一个失败更新可能重建队列或覆盖 dead | 确认失败更新、计数、终结删除均为正确条件操作；不因重复插入重置次数 |
| 迁移与模型 | 表名实际已不是纯失败流水，ID、File Record 关联、hash 类型未定 | 核对自动迁移入口与现有字段约束，独立 MySQL 探针验证 |
| 存储错误分类 | 删除不存在对象的 SDK 行为、权限错误和取消语义尚未核对 | 阅读现有适配器及依赖文档，验证分类和幂等删除，不泄漏原始错误 |
| Outbox 生命周期 | 未配置不注册 worker；已配置失败会 dead；恢复入口未验证 | 核对状态和事件事务、pending/dead 保留及人工入口；区分 Consumer 死信 |
| 旧 cleanup 职责 | 原有两项清理仍存在，三个 5 分钟刚好占满 15 分钟 | 明确旧任务顺序与预算；处理调度开销和父取消，不能保证后项一定获满 5 分钟 |
| 日志适配与口径 | 新字段不在白名单；高优先级告警不是已证明存在的告警系统；不存在对象的统计矛盾 | 同步安全白名单与日志文档，明确等级、字段类型和计数不重复规则 |
| 不受 broker 门控的过期 | 未配置时过期事件仍写 Outbox，仍可能有待投递记录 | 不能声称“跳过发布就完全消除未配置时 Outbox 积压”；明确该保留边界 |

## 11. 后续落地与验收输入

本次只沉淀讨论，不修改生产代码、数据库、主规格或已有归档，不执行 Git 提交。

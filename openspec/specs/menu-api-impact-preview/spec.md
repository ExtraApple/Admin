# menu-api-impact-preview Specification

## Purpose

菜单与 API 高影响配置变更的服务端预览和指纹保护契约，确保管理员能够在无副作用的前提下确认影响范围，并在提交时检测并发变更。

## Requirements

### Requirement: Server-side configuration impact preview

The system SHALL provide read-only impact preview operations for menu and API configuration changes:

- `POST /api/admin/menus/impact-preview`, protected by the existing `admin.menus.get` permission;
- `POST /api/admin/apis/impact-preview`, protected by the existing `admin.apis.get` permission.

A preview request SHALL identify a supported operation and its normalized candidate target. Supported menu operations SHALL include create, update, delete, bind APIs, clear APIs, and route synchronization. Supported API operations SHALL include metadata update, delete, route synchronization, permission synchronization, and button-menu generation.

The response SHALL include a stable operation name, normalized target summary, `preview_fingerprint`, affected menu/API identifiers, affected role and user counts, `access_version_change`, `requires_confirmation`, and synchronization additions/skips/conflicts where applicable. It SHALL NOT include credentials, raw SQL errors, cookies, tokens, or user-sensitive details beyond the approved counts and identifiers.

#### Scenario: Preview has no business side effects

- **WHEN** an authorized administrator requests a menu or API impact preview
- **THEN** the system validates the candidate against the same domain rules as the corresponding write
- **AND** the system returns the impact summary and fingerprint
- **AND** the system SHALL NOT modify menus, APIs, permissions, relations, access versions, cache state, or route registrations

#### Scenario: Preview reflects current Route Catalog facts

- **WHEN** an API preview or synchronization preview is requested
- **THEN** the system reads the current validated Route Catalog snapshot
- **AND** it identifies metadata-only, catalog-only, matched, and static-access-mismatch states
- **AND** it SHALL NOT treat database metadata as a source of Gin routes

#### Scenario: Preview rejects invalid configuration

- **WHEN** the candidate contains an invalid menu type combination, unknown parent, invalid API binding, duplicate path, or unsupported operation
- **THEN** the system returns the existing domain validation or conflict error
- **AND** it SHALL NOT return a successful fingerprint
- **AND** it SHALL NOT write any business fact

### Requirement: Fingerprint-guarded high-impact writes

High-impact menu/API writes SHALL accept an `expected_fingerprint` generated by a current preview. High-impact operations include menu create/update/delete, menu API bind/clear, menu synchronization, API permission/status/delete changes, API synchronization, permission synchronization, and button-menu generation.

The fingerprint SHALL be a 64-character lowercase hexadecimal SHA-256 digest over the current relevant configuration facts, the current Route Catalog snapshot summary, and the normalized candidate operation. The fingerprint SHALL be stateless and SHALL NOT be stored as a credential or persisted server-side.

#### Scenario: Current fingerprint permits a write

- **WHEN** a high-impact write includes an `expected_fingerprint` matching the fingerprint recomputed after the transaction locks its deterministic target set
- **THEN** the system applies the existing atomic write behavior
- **AND** the response reflects the committed result

#### Scenario: Stale fingerprint rejects a write

- **WHEN** a high-impact write includes a fingerprint that no longer matches the locked current facts
- **THEN** the system returns the existing `NAV_CONFLICT` or `API_META_CONFLICT` according to the owning module
- **AND** the system SHALL NOT modify the candidate resource, relations, permissions, roles, or access versions
- **AND** the client SHALL be required to request a new preview before retrying

#### Scenario: Missing or malformed fingerprint

- **WHEN** a high-impact write omits the required fingerprint or provides a value that is not a 64-character lowercase hexadecimal SHA-256 digest
- **THEN** the system returns the owning module's validation error
- **AND** the system SHALL NOT partially apply the write

### Requirement: Preview and commit use the same normalized facts

The preview path and the write path SHALL share normalization, dependency discovery, affected-role calculation, and conflict classification logic. A successful preview SHALL NOT guarantee a later write if another valid configuration change commits first.

#### Scenario: Concurrent change after preview

- **WHEN** another administrator changes a relevant menu, API, permission, binding, role, or Route Catalog fact after a preview succeeds
- **AND** the original administrator submits the old fingerprint
- **THEN** the write returns a conflict without automatic retry or overwrite
- **AND** the original candidate remains available to the client for explicit comparison and resubmission

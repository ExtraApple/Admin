## Context

当前角色删除清三个Authorization关系，Navigation.role_menus未接清理；普通UpdateRole没有专用范围入口的清custom步骤。各普通First预读不能证明与删除提交一致，真实FK=0证据只适用于审计自建schema。

依据[proposal](proposal.md)及其引用审计/裁决；本文件描述未来实施，不代表已改代码或执行验收。实际路径遵ADR0006的internal业务模块、caller-owned Contract与App唯一组合根，不沿用已登记为旧提示的顶层技术目录。

## Goals / Non-Goals

**Goals:**

- 从custom切走时两个角色修改入口都清理旧custom关联；普通角色删除同事务清用户/权限/数据范围/菜单映射，不删共享资源。
- 仍有普通角色custom引用时拒绝组织删除，停用角色或无成员不豁免，不自动改成self/all。
- 所有现有新增关系写入与删除/停用共享目标行锁及当前读取协议，删除先完成则拒绝新引用；绑定先成功可随后合法删除并清理其新增引用和用户版本。
- 软删普通旧成员只允许在管理范围与保护前提下受控移除，不可重新加入，不删除版本，不因恢复身份复活被清除归属。
- 失败只回滚本请求，保留其他并发合法胜方；不承诺所有重叠请求必有一方失败。

**Non-Goals:**

不增加全局关系修复器、数据库级级联删除、S3多菜单传播策略、组织移动影响算法或Seed全轮事务，不预先宣称所有锁竞争都成功。

## Decisions

### 1. 目标对象行是关联生命周期提交屏障

现有新增绑定、集合替换、对象停用/删除都在同一Context事务锁对应目标行后做当前读取；同一对象族按ID升序。角色绑定/删除共享角色行，API绑定/停用/删除共享API行，组织引用先进入C4父图协议。

**理由与替代方案**：删除拿到目标锁后重新读取实际关联/用户集合，新增关联方也必须锁该目标，避免预读后新增用户被清关系却漏版本。不同对象族仍可能锁竞争，允许既有Runner失败/重试但不承诺无死锁。

### 2. 生命周期组合由事实owner编排

Authorization删除普通角色通过caller-owned Navigation清理能力删除role_menus，其他关系仍由Authorization写；App注入并贯通事务，不跨模块import Adapter或共享GORM Model。API/Menu仍由既有Navigation协调。

**理由与替代方案**：不做数据库全局级联或新生命周期框架，不删除共享Menu/Permission。所有现有生产关系建立路径，包括适用Seed建立引用步骤，必须尊重相同目标存在性屏障而不套管理员本人保护。

### 3. custom清理与组织阻删是明确政策

普通UpdateRole和专用入口切到非custom调用同一owner关系维护；组织删除在锁定组织/父图后通过最小Authorization引用查询检查当前custom，角色停用和无成员不豁免。

**理由与替代方案**：不自动降级self/all，不清空仍活动custom来方便删除。角色删除与范围切换先释放引用后组织才能合法删除。

### 4. 软删旧成员与正常新增分开

增加仅供受控清理的安全身份事实查询，包含Deleted/保护与适用范围，不返回密码/邮箱验证秘密。正常目录仍排除软删用户；清理旧普通关系不删版本，恢复不重建关系。

**理由与替代方案**：不把Unscoped应用于所有公开目录，不自动修所有历史孤儿，不把停用当删除。

### 5. 合法先后与失败边界

绑定先提交可随后合法删除，删除前的影响集合必须在锁后读；删除先完成的新绑定按入口现有不存在/状态错误拒绝。当前目标/关联读用锁定current read，失败仅回滚本请求。

**理由与替代方案**：不统一所有错误为409，不要求并发胜方也回滚；版本按用户ID去重有序处理，外部缓存只在最外层提交后做。

### 实施与规格发布依赖

- 功能/写入协议前置：`enforce-protected-authorization-assignments`、`fix-concurrent-organization-moves`、`fix-menu-api-code-consistency`
- 共享Requirement发布基线：`enforce-protected-authorization-assignments`、`fix-menu-create-status-preservation`
- 本delta对重复Requirement使用包含前置增量的完整正文，不能乱序归档覆盖。功能依赖与发布依赖不是同一含义；无功能依赖的源码工作可独立，但发布须按此基线。每个前置必须先实施、验证并按流程同步到主规格；若主规格另有变化，合并保留其新增场景，不以旧全文覆盖。

## Risks / Trade-offs

- 只让删除加锁而绑定不参与 → 清单覆盖各现有写入者与App桥接，受控真实交错验证双方及实际版本集合。
- 锁内沿旧RR快照或预读用户集合 → 目标锁后重读并观察真实SQL暂停点；关系清理与所有版本失败全回滚。
- 新旧实例协议混跑 → 停写全量切换；不靠无FK环境的请求时检查承诺并发完整性。

## Verification

- 角色删除清四类映射但共享资源保留；第二个用户版本失败时包括role_menus在内全回滚。
- custom先提交阻删、组织先删拒custom；停用/无成员仍阻删，非custom切换两个入口都清旧关联。
- 角色/组织绑定先提交后删除可两次成功，删除包含新关联用户版本；反序绑定不能重建已删引用。
- API先停用拒新绑定，绑定先完成后停用可保留关系且访问拒绝；后续合法删除清关系并失效。
- 软删先完成不能正常新增；受控清理旧普通关系需范围/保护，恢复不还原；父菜单删除与子级新增不得绕过有子拒删。

只为真实消费者行为/边界保留适用回归；HTTP权限、跨模块事务和并发需要真实存储/原程序场景，Fake或SQLite仅保留自身局部效力。当前只创建工件，未执行这些检查。

## Migration Plan

不新增FK或批量修历史数据。先实施保护前提及C4/C3，停相关写流量并切换全部写实例到共同引用协议；恢复前跑真实交错与回滚门禁。回滚也必须停写全量切换，保留授权版本和业务数据；历史孤儿仅报告，不未经授权删除。

实施前确认上述依赖及既有DDL/装配，不打印凭据。此变更不新增HTTP路径、Redis key、MinIO bucket或权限码；涉及的现有入口和表见proposal。实施后更新对应审计状态与去敏证据，不能把剩余C6风险一并标完成。

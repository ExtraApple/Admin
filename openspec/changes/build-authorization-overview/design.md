## Context

当前 `web/src/components/WorkbenchShell.tsx` 的 `WorkbenchHome` 会把登录用户重定向到第一个可见管理模块，超级管理员没有统一的授权核对入口。角色详情页已经能够展示部分配置风险，但风险识别、影响摘要和首页导航没有统一读取模型；如果由前端并行请求角色、用户、菜单和组织接口再自行计算，会产生不一致快照并复制授权规则。

本 change 延续 ADR 0006 的固定一级模块和调用方 Contract 约束，新增能力由 Authorization Application 的读模型提供，App 负责装配，HTTP Adapter 负责协议，前端只呈现服务端事实。首版不新增数据表、Redis key、MinIO bucket 或历史授权事件存储。

## Goals / Non-Goals

**Goals:**

- 提供按操作者数据范围裁剪的授权总览和完整风险清单。
- 由服务端统一计算配置风险、目标对象聚合、潜在影响范围和稳定排序。
- 让超级管理员进入工作台后先看到授权总览，而不是自动进入角色列表。
- 使用只读范围带表达当前操作者的真实数据范围。
- 在桌面和移动端以风险优先的布局展示加载、空、错误和可访问状态。
- 保持四字段响应信封、Route Catalog、API Metadata 和稳定权限码约束。

**Non-Goals:**

- 不计算每个用户的最终有效权限，不展示精确用户级授权推导。
- 不统计在线会话，不保存授权历史，不新增审计时间线或审批队列。
- 不在总览或风险清单内执行启用菜单、补权限、调整角色或组织等写操作。
- 不实现组织创建；该能力另行处理。
- 不新增 `internal/adminworkbench` 一级模块，不改变既有角色、用户、组织详情写入接口。

## Decisions

### 1. Authorization Application 持有聚合读模型

Authorization Application 增加授权总览查询用例，并在自身 Application 层定义访问角色、菜单、用户和组织所需的最小 Contract。跨模块实现由 App 注入；不得导入其他模块的 HTTP Adapter、GORM Model 或直接暴露数据库连接。HTTP Adapter 只绑定查询参数、调用用例并写入统一响应。

**替代方案**：由 `internal/app` 直接组合查询会把业务规则推入组合根；由各模块返回片段再由前端拼接会分散规则并削弱快照一致性。

### 2. 两个只读入口，共享一套服务端风险规则

新增：

- `GET /api/admin/authorization-overview`，权限码 `admin.authorization.overview.get`，返回范围、摘要和按影响范围排序的前 10 个风险对象。
- `GET /api/admin/authorization-risks`，权限码 `admin.authorization.risks.get`，返回完整分页风险对象，支持 `page`、`size`、`kind`、`resource` 和 `keyword` 查询。

两个入口共享同一 Application 读模型和风险分类器。总览的 `total` 表示风险对象数量，不是具体问题数量；风险对象按潜在受影响用户数降序、潜在受影响组织数降序、资源类型和 ID 的稳定顺序排列。

### 3. 风险按目标对象聚合

首版风险类型固定为：

- `disabled_assigned_menu`
- `missing_menu_permission`
- `used_role_without_permissions`
- `managed_user_without_role`

一个角色或用户返回一条风险对象，包含 `issue_count` 和有限的 `issue_kinds`。总览只返回前 10 个对象；超出部分必须从专用风险清单页继续核对。启用但未被使用的空角色、空组织和普通初始化空状态不报警。

### 4. 读取一致性与范围安全

一次查询中 `scope`、`summary` 和 `risks` 必须来自同一个逻辑读取快照；实现可以使用现有事务／仓储组合，但不能让不同部分使用互不相关的用户请求或全局缓存结果。所有角色、用户、组织数量和风险对象都必须先应用操作者数据范围；超级管理员拥有全部范围只是当前角色事实，不改变接口的范围感知语义。

接口只返回稳定数据码和计数。会话影响只返回 `revalidate_on_next_request` 规则说明，不返回在线会话数量。空集合序列化为 `[]`，业务错误继续使用现有四字段错误信封。

### 5. 工作台首页和风险清单的前端结构

`WorkbenchHome` 对拥有 `admin` 角色且具备总览权限的用户渲染授权总览；没有该能力的用户保留现有可用模块导航行为。新增授权总览页面和风险清单页面，API 类型放入集中 `web/src/lib/models.ts`，请求通过集中 `api` Client 完成。

桌面端采用侧边导航、顶部面包屑、只读范围带、左侧风险列表和右侧授权摘要；移动端改为单列，风险对象使用全宽卡片。风险对象只能跳转到已有角色／用户详情，首页不执行写操作。风险颜色表达“需要核对”，不表达安全事件严重等级。

### 6. 发布和路由契约

后端先注册 Route Descriptor、权限码、OpenAPI 响应 Schema 和 API Metadata，再部署前端。前端沿用既有四字段解析、错误本地化和受保护路由 Guard。新接口不改变既有接口响应。

## Risks / Trade-offs

- [风险] 聚合查询跨越多个模块，查询成本可能高于现有单资源列表。→ [缓解] 首版只返回计数、聚合风险和固定前 10 条；完整风险使用分页清单，并为查询增加服务端测试和必要索引评估。
- [风险] `potentially_affected_*` 容易被误解为最终有效权限人数。→ [缓解] 字段命名和 UI 文案明确使用“潜在影响范围”，不展示最终权限结论。
- [风险] 风险规则随角色、菜单或用户关系变化而漂移。→ [缓解] 两个路由共享一个 Application 风险分类器，并为每个风险类型写行为测试。
- [风险] 前端先部署时新接口不存在。→ [缓解] 发布顺序固定为后端路由和权限元数据、后端验证、前端部署；回滚时先回滚前端再回滚后端。
- [风险] 范围带被误解为可切换的临时数据范围。→ [缓解] 只读展示当前操作者 `data_scope`，不提供切换控件，并在规格中区分授权事实和查看过滤。
- [风险] 现有超级管理员权限同步尚未包含新权限码。→ [缓解] 通过 Route Catalog/API Metadata 权限同步和受保护 `admin` 角色兜底验证新权限；不得写死前端放行替代后端裁决。

## Migration Plan

1. 在 Authorization Application 增加读模型 Contract、风险分类和查询服务。
2. 在 App 组合根装配跨模块查询能力，注册两个 Route Descriptor，补充 API Metadata、权限码、OpenAPI 和测试。
3. 验证现有管理员和超级管理员访问边界、空集合、风险排序和响应信封。
4. 增加前端授权总览模型、路由、首页入口、风险清单页、范围带和响应式状态。
5. 先部署后端，再部署前端；不需要数据库迁移或历史数据回填。
6. 回滚时先恢复前端旧首页，再移除后端新增路由和权限元数据；既有角色、用户、组织数据不受影响。

## Open Questions

无用户可见行为上的未决问题。实现时只需在现有模块 Contract 约束内确定具体接口名称和仓储查询拆分，并保持本设计中的外部响应字段与排序语义。

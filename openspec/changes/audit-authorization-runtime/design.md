## Context

C6b 当前不是空白授权系统，而是已有认证、授权版本、RBAC、用户生命周期和组织范围契约的运行时证据尚未完全闭合。已确认的 C1-C6 与相关目标已有独立修复和局部验收；本 change 只针对剩余授权运行时风险，不重跑已确认反例，也不把菜单投影、文件、消息、日志或候选设计混入安全真值。

审计必须从真实 HTTP 入口验证 handler、service、model、JWT、MySQL 和 Redis 的组合行为。共享数据库、生产 Token、Redis 内部验证码答案和 mock-only 结果均不作为证据。

## Goals / Non-Goals

**Goals:**

- 建立固定隔离身份、角色、组织、授权版本和 Token 夹具。
- 通过真实 HTTP、真实 JWT、独占 MySQL／Redis 执行四波共 32 个最小 Case：Token／版本、授权变更与事务、数据范围与保护对象、确定性并发。
- 验证现有状态码、错误码、授权版本推进、旧 Token 失效、关系持久化和失败回滚契约。
- 将每个风险域归类为通过、发现缺陷或证据缺口。
- 生成一份审计报告和三份去敏机器证据，保留可复核的代码基线和运行边界。

**Non-Goals:**

- 不修改产品代码、主规格、永久测试、路由、权限码、模型、Redis key、MinIO bucket 或第三方依赖。
- 不重新设计授权策略、全局最小失效集合、I3 复杂依赖图或 S3/S4/S5 候选语义。
- 不把菜单可见性当作 API 授权真值；菜单只做独立投影观察。
- 不执行文件、消息、日志、Route Catalog 或全量 API 端点审计。
- 不使用随机压力测试替代确定性事务和并发证据。

## Decisions

### 1. 使用等价类矩阵，而不是全组合穷举

以操作者、目标对象、授权范围、变更类型和 Token 状态构造固定等价类。每个等价类覆盖正常、拒绝和关键失败路径；不对所有角色、组织和权限做笛卡尔积。

备选方案是只执行 happy path，证据不足；或穷举全部组合，成本高且重复，均不采用。

### 2. 以真实 HTTP 和隔离基础设施作为一级证据

审计使用当前仓库编译的真实服务、独占 MySQL、Redis 和临时 schema，通过真实 HTTP 发送请求。源码、现有 Go 测试和 LSP 结果只作为二级解释证据；SQLite、mock handler 或只调用 Service 不单独证明生产事务行为。

审计 Runner、临时配置、容器、schema、二进制和凭据由本 change 拥有，完成后清理。

### 3. 采用现行错误分类和授权版本契约

缺失 Access 版本返回 `401 AUTHN_TOKEN_INVALID` 且不补行；Refresh 无效返回 `401 AUTHN_REFRESH_TOKEN_INVALID`；已建立身份但用户禁用返回 `403 IDENTITY_*`；真实存储故障返回安全 `5xx`；逐人角色／组织 CAS 冲突分别返回 `409 AUTHZ_CONFLICT`／`ORG_CONFLICT`。每个 Case 同时核对 HTTP、错误码、Token 是否签发、最终关系和授权版本。

### 4. 把授权安全真值与菜单投影分开

API／服务端授权结果决定安全结论；`/api/user/context` 和菜单只作为导航投影观察。菜单隐藏不能证明 API 拒绝正确，菜单可见也不能证明 API 允许正确。投影偏差和授权越权分别分类，不互相覆盖。

### 5. 以事务不变量验证变化、no-op 和并发

真实变化必须只推进适用用户版本一次；当前版本合法 no-op 不推进版本；过期版本的真实变化和 no-op 都必须冲突；保护／越权请求不得留下关系或版本变化；业务写入、版本初始化、锁定、提升或提交任一步失败时整次事务回滚。

并发使用数据库锁等待和两条真实 HTTP 请求制造确定性交错。最多一个旧版本请求成功，其他请求返回对应冲突；最终版本不倒退，不因重试产生重复提交。

### 6. 审计结果采用三态闭环

每个风险域只允许“通过”“发现缺陷”“证据缺口”。环境障碍或未覆盖路径不能写成通过；发现明确偏差时保存原始去敏证据并在本 change 内停止修复，后续修复另建 change。

### 7. 使用一份总报告和三份机器证据

报告写入 `docs/reviews/contract-readiness-c6b-authorization-runtime.md`；机器证据分别记录 Token／版本、授权变更、数据范围与并发结果。所有记录使用去敏请求、响应、版本摘要、关系摘要、等待点和代码基线，不保存密码、JWT、captcha 答案或 DSN。

## Risks / Trade-offs

- [Risk] 隔离环境启动或故障注入失败会阻止部分 Case → 将其记录为证据缺口，保留已完成 Case，不把障碍改写成产品通过或缺陷。
- [Risk] 现有历史证据与当前代码基线不一致 → 每个结果记录当前代码基线和独立运行环境，历史证据只作为适用性说明。
- [Risk] 共享授权版本和组织依赖导致并发结果难以归因 → 使用单目标、固定版本和数据库 barrier，保存最终关系及版本快照。
- [Risk] 菜单显示与 API 授权混淆 → 报告将导航投影与安全授权分别列为独立结论。
- [Risk] 32 个 Case 仍可能遗漏未列入的业务入口 → 明确报告代表性覆盖边界，不声称全端点或全 C6b 完成。

## Migration Plan

不涉及生产迁移、数据库 schema 变更、Redis key 迁移、MinIO bucket 变更或部署切换。审计只创建独占临时 schema、临时运行资源和去敏证据；结束后删除本 change 拥有的资源。

## Open Questions

无需要在实施前裁定的产品语义。运行过程中若发现当前规格与实现无法归类，暂停该 Case，记录为证据缺口或独立语义问题，不在本 change 内猜测并修复。

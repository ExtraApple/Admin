## Context

本 change 是授权运行时有限审计之后的第二个顶层风险切片：资源与生命周期。当前已发布 `file-management`、`internal-messaging` 和 `logging` 规格已经描述消息可见性、消息图片用途、文件对象与元数据边界、清理队列、轮转、审计字段和查询范围；本 change 不重新设计这些契约。

审计对象跨越 `internal/app`、`internal/files`、`internal/messaging`、`internal/audit` 及其 HTTP、GORM、MySQL、Redis、MinIO 和后台任务边界。现有服务测试、SQLite 测试、C5 定向验收和静态源码观察只能证明局部行为，不能单独证明真实认证、可见性、跨存储失败和后台日志组合路径。

审计按一个 A2 报告交付，包含三个章节：

1. 消息当前可见性与撤销边界；
2. 文件、对象与元数据失败一致性；
3. 审计日志脱敏与范围查询。

## Goals / Non-Goals

**Goals:**

- 固定当前代码基线、已发布规格、运行配置形状和去敏环境边界。
- 使用真实 App 组合根、HTTP／JWT、独立 MySQL schema、Redis namespace 和 MinIO 对象，验证代表性正常、拒绝、失败和确定性交错。
- 覆盖超级管理员、受限管理员、发送者、当前受众、失去受众资格用户、组织外用户以及删除私信关系后的原收件人。
- 验证私信、群发和公告的列表／详情／图片可见性；撤销、过期、动态受众变化和私信关系删除后的拒绝与无泄露边界。
- 验证普通文件上传补偿、删除失败、轮转失败回滚，以及消息图片绑定、清理登记、对象删除、重试、`dead`、终结和迟到结果。
- 验证 HTTP 与后台文件／消息操作的日志字段白名单、敏感信息禁止项、操作者／组织范围、权限、分页和 total。
- 对每个 Case 保存前置事实、操作、HTTP／错误结果、数据库投影、对象存储投影和日志投影；所有证据去敏。
- 将结果分类为契约一致、实现偏差、证据不足或语义待裁决；发现明确偏差时停止本 change 内修复，后续另建修复 change。

**Non-Goals:**

- 不修改产品代码、当前主规格、永久测试、路由、权限码、数据模型、Redis key、MinIO bucket 或第三方依赖。
- 不创建新的产品能力、审计 API、清理控制面、运维命令或人工 HTTP 处置接口。
- 不把 C5 历史设计讨论、未来通知 Consumer、完整 RabbitMQ／Consumer／DLQ 算法、头像、历史文件批量重新验证或全消息功能混入本 change。
- 不执行随机压力测试、生产存量删除、真实生产部署、跨实例容量基准或 A3 装配与响应契约审计。
- 不把 fake、SQLite、单次无异常返回或菜单投影单独当作真实安全与跨存储通过证据。

## Decisions

### 1. 使用现行规格作为唯一判据

本 change 读取当前 `openspec/specs/file-management`、`openspec/specs/internal-messaging` 和 `openspec/specs/logging` 的 Requirement／Scenario，并以当前 runbook 解释部署和运维边界。历史 review、未来候选目标和未批准设计只作为背景，不可升级为当前缺陷。

备选方案是把 C5 设计讨论中的所有未闭合项都纳入本轮；这会把审计变成重新设计，并违反已经确认的有限 A2 边界，因此不采用。

### 2. 采用真实组合路径作为一级证据

正常创建、发布、撤销、关系删除、列表、详情和图片读取优先通过真实 HTTP／JWT／生产组合根执行。数据库只用于固定夹具和无法通过业务入口构造的故障前置。MySQL、Redis 和 MinIO 使用独立资源；共享开发库和生产数据不参与。

源码、LSP、现有 Go 测试、SQLite 和 fake 只作为解释或局部证据。它们不能单独证明动态受众、真实权限中间件、对象存储补偿或跨存储事务行为。

### 3. 以三个固定矩阵组织 Case

消息可见性矩阵覆盖私信、群发、公告和消息图片，分别核对当前可见、撤销、过期、受众资格变化、私信关系删除和组织外访问。不可见结果必须同时确认正文、图片和存储状态不泄露。

文件生命周期矩阵覆盖对象上传成功而数据库失败、对象删除失败、清理登记失败、对象删除失败、对象已删而数据库终结失败、同一重试的多实例竞争、迟到失败结果以及轮转／清理交错。

审计日志矩阵覆盖 HTTP 文件／消息操作、C5 后台任务以及 Outbox／Consumer／DLQ 与资源事实直接相关的路径。允许字段限于稳定操作、操作者／目标／组织 ID、结果、稳定错误码、任务／队列 ID、重试次数、时间和计数；正文、HTML、图片、bucket、object key、签名 URL、Token、凭据、邮箱／手机号和原始基础设施错误不得出现。

### 4. 使用确定性交错，不使用随机并发

通过数据库 barrier、锁等待和受控对象存储状态构造绑定与清理登记、轮转与清理、多实例重试、对象删除与迟到失败、撤销／过期与读取之间的固定顺序。每个交错记录赢家、失败方、最终数据库事实、对象事实和日志事实。

随机压力测试无法归因具体不变量，且属于独立容量审计，因此不采用。

### 5. 分离真实故障与受控故障注入

权限拒绝、对象不存在、缺桶、对象存储权限、超时、Broker 断连等可复现基础设施状态尽量使用真实隔离依赖。难以稳定触发的数据库提交失败可使用测试专用故障注入，但证据必须标注注入层级，不冒充真实物理故障。

所有环境障碍都分类为证据不足或验证阻塞，不改写成产品通过，也不为获得绿色结果添加产品 fallback。

### 6. 一份报告、一份机器证据

总报告写入 `docs/reviews/contract-readiness-a2-resource-lifecycle.md`；机器证据写入 `docs/reviews/evidence/a2-resource-lifecycle.json`。JSON 只保存去敏 Case ID、代码基线、状态／错误码、关系摘要、队列／版本摘要、对象存在性分类、日志字段摘要和清理结果，不保存凭据、JWT、Authorization header、DSN、对象路径或原始错误。

报告按“契约一致／实现偏差／证据不足／语义待裁决”分节，明确适用前提、实际入口、已证明事实、未覆盖边界和下一步归属。一个章节通过不替代其他章节通过。

### 7. 使用审计型 delta 固定证据契约

OpenSpec 严格校验要求本 change 有一个 delta；因此新增 `specs/resource-lifecycle-audit/spec.md`，只描述本 change 的审计证据结构、分类和去敏边界。它不是运行时产品能力，不替代也不修改 `file-management`、`internal-messaging` 或 `logging` 的当前 Requirement。

归档时必须显式使用 `--skip-specs`，避免把审计流程同步进产品主规格。若审计发现产品偏差，保留去敏证据并停止在本 change 内修复；后续修复或规格裁决必须创建独立 change。

## Risks / Trade-offs

- **真实环境成本高**：MySQL、Redis、MinIO 或服务启动失败会阻塞部分 Case；保留已完成证据，并将受阻路径标为证据不足。
- **覆盖不是全端点保证**：代表性入口不能推出全部 `/api/admin` 或全部消息 API 正确；报告必须写明入口和不覆盖范围。
- **数据库与对象存储无法原子提交**：设计只能验证登记先行、补偿、重试和可恢复定位，不能声称跨系统事务。
- **动态受众状态可能随时间变化**：每个 Case 固定 UTC `now`、成员关系和消息状态，保存夹具摘要，避免把时间漂移误判为权限结果。
- **日志字段可能被多层重新编码**：同时核对 RuntimeLogger 输入和最终 sink 输出，不能只检查调用点参数。
- **历史 C5 证据与当前基线可能不一致**：只复用适用于当前代码和规格的证据；其余重新建立，不把归档 tasks 勾选等同于本轮 A2 通过。

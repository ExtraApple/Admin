## MODIFIED Requirements

### Requirement: 菜单 CRUD
系统 SHALL 允许管理员创建、修改和删除菜单记录。

创建菜单 SHALL 区分status未提供与显式合法值；显式0表示停用，显式1表示启用。只有未提供或现行无效值才使用默认启用，响应与实际存储 SHALL 一致。

菜单子级存在检查与父引用创建 SHALL 在提交时保持一致；有子菜单不得删除的保证不能被并发新增父引用绕过。普通菜单合法删除可清理包括admin在内的适用配置引用，但不得借此改写受保护用户归属。

菜单icon/component与合法path更新 SHALL 表达字段存在性；遗漏保持，明确空字符串在满足该字段现有类型/路径/引用前提时清空，非空替换。必填name不可显式清空；permission_code仍按独立绑定码契约处理，不在此新增其空码政策。

配置写入 SHALL 先满足身份、权限、保护、引用、适用范围及既有并发前提，再比较完整规范化目标事实；合法同值或等价配置成功且不提升版本。真实字段或派生关系变化仍按现行依赖规则失效；不能用RowsAffected、更新时间或最终有效权限相同代替业务事实比较。

#### Scenario: 创建菜单
- **WHEN** 管理员提交菜单名称，以及可选的路径、组件、图标、权限码、父级、排序、类型和状态
- **THEN** 系统创建菜单
- **AND** 当类型或状态未提供或无效时，系统使用默认值

#### Scenario: 创建按钮菜单
- **WHEN** 管理员创建 `type = 3` 的按钮菜单
- **THEN** 系统允许菜单路径为空
- **AND** 系统可保存该按钮菜单绑定的 `permission_code`

#### Scenario: 菜单路径冲突
- **WHEN** 创建或修改请求使用了已被其他菜单占用的路径
- **THEN** 系统拒绝请求

#### Scenario: 父级菜单指向自己
- **WHEN** 修改请求将 `parent_id` 设置为当前菜单自身 ID
- **THEN** 系统拒绝请求

#### Scenario: 修改菜单
- **WHEN** 管理员提交有效的菜单变更字段
- **THEN** 系统只更新提交的字段
- **AND** 如果没有可更新字段，系统拒绝请求

#### Scenario: 删除存在子菜单的菜单
- **WHEN** 管理员删除仍有子菜单的菜单
- **THEN** 系统拒绝删除

#### Scenario: 删除叶子菜单
- **WHEN** 管理员删除没有子菜单的菜单
- **THEN** 系统删除该菜单对应的角色菜单关联
- **AND** 系统删除该菜单对应的菜单 API 关联
- **AND** 系统硬删除菜单记录

#### Scenario: 显式创建停用菜单
- **WHEN** 管理员向POST /api/admin/menus提交其他字段合法且status为0的请求
- **THEN** 系统 SHALL 成功保存停用菜单，响应和数据库status均为0

#### Scenario: 创建状态遗漏与合法启用
- **WHEN** 合法创建省略status或显式提交1
- **THEN** 系统 SHALL 按现行默认或显式值保存启用状态，响应与存储一致

#### Scenario: 无效创建状态使用既有默认
- **WHEN** 其他创建字段合法，但status不在合法0/1范围
- **THEN** 系统 SHALL 使用现行默认启用状态，不把合法0归类为无效

#### Scenario: 创建事务中版本失败
- **WHEN** 菜单创建后同一事务的授权版本处理失败
- **THEN** 系统 SHALL 回滚菜单及本次全部版本写入，不返回伪成功菜单

#### Scenario: 菜单删除与子菜单创建交错
- **WHEN** 子菜单先合法提交，或父菜单删除先成功提交
- **THEN** 系统 SHALL 分别拒绝仍有子级的删除，或拒绝对已删除父菜单新增引用
- **AND** 失败请求不留下菜单、关系或版本写入；不新增未知parent_path解析政策

#### Scenario: 菜单可选属性清空与遗漏分开
- **WHEN** 合法菜单更新明确提交空icon或component，并省略其他可选字段
- **THEN** 系统 SHALL 清空指定属性，保持遗漏属性，不把显式空误判为没有更新字段

#### Scenario: 合法路径清空
- **WHEN** 请求明确清空path且满足当前菜单类型及其他既有路径合法性前提
- **THEN** 系统 SHALL 清空路径并保留现有唯一性、父级和权限绑定约束
- **AND** 不因本目标新增另一套菜单类型或路径政策

#### Scenario: 非法清空不部分提交
- **WHEN** 请求包含不可清空的名称或不满足交叉约束的路径变化
- **THEN** 系统 SHALL 拒绝整个请求，属性、关系及本次版本写入保持不变

#### Scenario: 菜单同值与真实展示变化
- **WHEN** 合法菜单字段全同值，或名称/图标/排序等配置真实变化
- **THEN** 系统 SHALL 对真正同值不提升版本；真实展示或权限配置变化仍按对应依赖失效

#### Scenario: 仅DTO同值不能掩盖派生修复
- **WHEN** 直接字段同值但本次合法写入仍须按既有绑定契约改变派生关系
- **THEN** 系统 SHALL 完成真实派生变化及对应事务版本处理，不伪装无变化

### Requirement: 角色菜单分配
系统 SHALL 允许管理员替换某个角色拥有的菜单列表，并 SHALL 在管理员查询分配结果时返回按 `sort asc, id asc` 排序的平铺已分配菜单项（含 `parent_id` 和 `status`），不以运行时用户菜单可见性或未分配父级的存在与否裁剪配置。

管理端直接替换admin角色菜单 SHALL 拒绝。普通角色菜单替换 SHALL 完整验证全部原始ID、存在性及适用管理前提，再去重；存在的普通停用角色与菜单允许预配置，不因此授予用户当前可见性或访问权限。

配置写入 SHALL 先满足身份、权限、保护、引用、适用范围及既有并发前提，再比较完整规范化目标事实；合法同值或等价配置成功且不提升版本。真实字段或派生关系变化仍按现行依赖规则失效；不能用RowsAffected、更新时间或最终有效权限相同代替业务事实比较。

#### Scenario: 分配菜单到角色
- **WHEN** 管理员提交角色 ID 和菜单 ID 列表
- **THEN** 系统清除该角色已有的角色菜单记录
- **AND** 系统插入本次提交的关联记录

#### Scenario: 查询角色菜单
- **WHEN** 管理员请求 `GET /api/admin/roles/:id/menus` 查询某个角色拥有的菜单
- **THEN** 系统返回该角色所有显式分配菜单的平铺列表，包括已停用菜单及每项的 `parent_id`、`status`，不按角色是否拥有菜单要求的权限码过滤
- **AND** 如果没有已分配菜单，系统返回空列表

#### Scenario: 仅分配子菜单或停用菜单
- **WHEN** 某角色只分配了子菜单而未分配其父级，或某已分配菜单随后被停用
- **THEN** 管理员查询该角色菜单时仍能看到这些已分配菜单及其状态
- **AND** 未显式分配的父级 SHALL NOT 作为已分配菜单返回

#### Scenario: admin角色菜单直接编辑拒绝
- **WHEN** 管理员直接修改admin角色菜单集合
- **THEN** 系统 SHALL 拒绝，不改变关联或版本

#### Scenario: 菜单非法目标与停用目标分开
- **WHEN** 普通角色请求包含0/不存在菜单，或仅包含合法存在但停用菜单
- **THEN** 系统 SHALL 对非法目标整次拒绝，对满足其他前提的停用普通菜单允许配置
- **AND** 管理员配置读取与用户运行时可见性仍分离

#### Scenario: 等价角色菜单配置
- **WHEN** 所有前提满足且去重目标菜单集与当前显式配置相同
- **THEN** 系统 SHALL 成功且不提升版本，不按运行时可见性重算配置目标

### Requirement: 菜单 API 联动
系统 SHALL 允许管理员把菜单按钮和 API 元数据绑定，并保证菜单权限码、API 权限码、角色授权和相关用户会话状态一致。

菜单绑定API SHALL 先校验原始api_ids中每个ID，再仅对合法ID去重；零ID SHALL 整次拒绝，不得在归一化时静默丢弃。此要求同样适用于直接调用Application的现有生产路径。

普通菜单修改中的权限码变更 SHALL 消费与菜单绑定相同的既有直接联动规则，而不得只更新menus。菜单字段、直接绑定API、对应权限和授权关联及本次会话失效 SHALL 在同一最外层事务完成；响应 SHALL 基于实际提交结果。

菜单API绑定列表 SHALL 保持非空；不能借完整替换语义新增空数组解绑。API启用且需要认证的明确前提不因其他停用普通配置目标可预配置而放宽。

API启用、存在及需要认证 SHALL 是新绑定提交前提。绑定先合法完成，后续合法停用可以保留配置关系；后续合法删除按现有生命周期清理。全部关联写入与版本处理 SHALL 共享最外层事务，失败仅撤销本次请求。

配置写入 SHALL 先满足身份、权限、保护、引用、适用范围及既有并发前提，再比较完整规范化目标事实；合法同值或等价配置成功且不提升版本。真实字段或派生关系变化仍按现行依赖规则失效；不能用RowsAffected、更新时间或最终有效权限相同代替业务事实比较。

#### Scenario: 菜单绑定 API
- **WHEN** 管理员向 `POST /api/admin/menus/:id/apis` 提交菜单 ID、API ID 列表和可选权限码
- **THEN** 系统校验菜单存在
- **AND** 系统校验 API 均存在、已启用且需要认证
- **AND** 系统 SHALL 在同一数据库事务中覆盖写入 `menu_apis`
- **AND** 系统 SHALL 同步菜单和绑定 API 的 `permission_code`
- **AND** 系统 SHALL 确保权限表存在对应权限码
- **AND** 新权限码已存在时系统 SHALL 合并并去重既有角色授权
- **AND** 仅配置事实真实变化时，系统 SHALL 在同一事务中使变更前后受影响用户的旧 token 失效

#### Scenario: 菜单绑定 API 失败
- **WHEN** 菜单、API、`menu_apis`、权限、角色授权或 token 版本任一步写入失败
- **THEN** 系统 SHALL 回滚本次绑定操作的全部数据库写入
- **AND** 菜单、API、权限关联和用户 token 版本 SHALL 保持事务开始前状态

#### Scenario: 查询菜单绑定 API
- **WHEN** 管理员调用 `GET /api/admin/menus/:id/apis`
- **THEN** 系统返回该菜单绑定的 API 元数据列表
- **AND** 如果没有绑定 API，系统返回空列表

#### Scenario: 删除菜单清理 API 关联
- **WHEN** 管理员删除叶子菜单
- **THEN** 系统清理该菜单对应的 `menu_apis` 关联

#### Scenario: 菜单权限变更实时生效
- **WHEN** 菜单绑定 API 或菜单权限码发生真实联动变更
- **THEN** 系统 SHALL 在保存权限关系的同一数据库事务中提升相关 token 版本
- **AND** 相关用户的旧 token SHALL 在事务提交后的下一次请求时失效

#### Scenario: 混合有效API与零ID
- **WHEN** 合法菜单绑定请求同时包含存在且可绑定的API ID与0
- **THEN** 系统 SHALL 以既有Navigation校验错误拒绝整次请求
- **AND** 菜单、API、menu_apis、权限、角色授权和用户版本均不留下该请求写入

#### Scenario: 合法重复API ID
- **WHEN** 其余前提合法的请求包含重复有效API ID
- **THEN** 系统 SHALL 去重后按既有绑定规则处理
- **AND** 不得创建重复关联，也不得将合法去重与丢弃非法ID混同

#### Scenario: 内部调用不能绕过原始校验
- **WHEN** 内部生产调用向同一菜单绑定用例传入混合有效与零ID
- **THEN** 系统 SHALL 同样拒绝且不写入关系或版本

#### Scenario: 菜单侧修改已绑定权限码
- **WHEN** 菜单与直接绑定API原本一致，管理员通过PUT /api/admin/menus/:id提交合法的新权限码
- **THEN** 系统 SHALL 同步菜单与这些直接绑定API的权限码，并按既有绑定码规则确保权限、合并去重角色授权
- **AND** menu_apis目标集合不因仅改码被改变，相关版本与事实共同提交

#### Scenario: 菜单侧联动中途失败
- **WHEN** 菜单改码过程中API、权限、角色授权或任一用户版本写入失败
- **THEN** 系统 SHALL 回滚该请求的全部菜单/API/权限/关系/版本写入
- **AND** 不得已提交菜单新码却保留直接绑定API旧码

#### Scenario: 未绑定菜单改码
- **WHEN** 合法菜单没有绑定API且提交权限码变更
- **THEN** 系统 SHALL 保留现有未绑定菜单的合法更新语义，不创建虚假API绑定

#### Scenario: 绑定菜单显式空码沿用既有解析
- **WHEN** 菜单侧显式空码进入已有绑定码解析，直接绑定API仍满足现有绑定前提
- **THEN** 系统 SHALL 使用与既有菜单绑定相同的权限码解析与失败语义
- **AND** 不新增解绑、授权撤销或多菜单传播优先级规则

#### Scenario: 空API集合不是解绑
- **WHEN** 管理员提交空api_ids请求
- **THEN** 系统 SHALL 拒绝，不清空既有绑定或改变任何版本

#### Scenario: API停用或删除先完成
- **WHEN** API已经停用或删除，随后新绑定进入提交判断
- **THEN** 系统 SHALL 按适用状态/不存在规则拒绝整次绑定，不过滤目标或重建对象

#### Scenario: 绑定先完成后停用保留配置
- **WHEN** 绑定合法提交后，API按现行契约合法停用
- **THEN** 系统 SHALL 允许保留绑定，运行时访问继续按禁用规则拒绝
- **AND** 不因此新增自动解绑、权限回收或菜单显隐政策

#### Scenario: 绑定与删除的版本原子性
- **WHEN** 合法绑定先提交，随后API删除清理新关联，或其中任一事务失败
- **THEN** 系统 SHALL 根据合法胜方实际依赖处理全部用户版本，失败事务不得残留自身部分变化

#### Scenario: 等价绑定还须比较派生事实
- **WHEN** API目标集合相同，最终解析的码、权限与授权关系也均无真实变化
- **THEN** 系统 SHALL 成功且不提升版本

#### Scenario: 相同API集合仍有真实码变更
- **WHEN** API集合相同但本次解析码或必须维护的权限/授权关系发生变化
- **THEN** 系统 SHALL 按真实联动原子提交并使适用用户失效

### Requirement: 前端路由同步菜单
系统 SHALL 能够根据前端路由元数据创建缺失的菜单记录。

合法菜单同步若仅正常跳过已有路径且没有新菜单或其他派生事实变化，SHALL 成功返回本次创建数零且不提升用户版本；此豁免不得绕过已有路由输入与父级解析前提。

#### Scenario: 同步创建新菜单
- **WHEN** 管理员向同步接口提交路由元数据
- **THEN** 系统为不存在的路径创建菜单记录
- **AND** 如果存在 `parent_path`，系统根据它解析父菜单
- **AND** 系统保存路由元数据中的 `permission_code`
- **AND** 系统返回本次创建的菜单数量

#### Scenario: 同步遇到已存在路径
- **WHEN** 提交的路由路径已存在于菜单表
- **THEN** 系统跳过该条数据

#### Scenario: 同步仅正常跳过不失效
- **WHEN** 本次合法同步的所有项均按现有规则跳过，且无任何派生事实写入
- **THEN** 系统 SHALL 返回真实本次创建数零，不额外使用户失效
- **AND** 未知parent_path如何处理保持独立未决范围，不由no-op政策替代

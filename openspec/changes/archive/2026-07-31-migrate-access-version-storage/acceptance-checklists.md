# 授权版本迁移里程碑验收清单

本文是 `migrate-access-version-storage` 的发布验收记录模板。所有检查项必须附带可复核证据；口头确认、仅有“测试通过”的描述或 SQLite 结果不能替代要求真实 MySQL 的证据。

## 使用规则

- 状态只允许填写：`未执行`、`通过`、`失败`、`不适用`。
- `不适用` 必须记录原因和批准人。
- 证据存放在当次发布记录中，建议路径：
  `docs/releases/<release-id>/access-version-storage/`。
- 命令栏中的测试名称是验收目标；相关测试尚未实施时保持 `未执行`，不得提前判定里程碑完成。
- 任一必选项失败时停止当前发布步骤，按设计文档中的停机回滚流程处理。
- SQLite 只作为快速反馈门禁；标记为 **MySQL 强制门禁** 的项目必须使用与生产主版本一致的真实 MySQL。

每项执行记录统一使用：

## 一、切换里程碑

切换里程碑的目标是安全地把授权版本唯一读取来源切换为
`user_access_versions`。本里程碑全部通过后，才允许
`restructure-layered-monolith` 开始实施；无需等待退出里程碑。

### A. 发布制品与部署护栏

- [ ] 单一发布制品同时包含：
  `EnsureVersion`、`EnsureAndIncrement`、只读新表、旧字段原子镜像和迁移逻辑。
  - 验证：记录制品版本、Commit 和构建产物摘要。
  - 证据：构建日志及制品 SHA-256。
- [ ] 部署清单校验通过，承载流量的实例不存在
  `legacy-users-token-version` 与任一新表读取模式混跑。
  - 验证：调用 `initialize.ValidateAccessVersionDeployment` 的部署检查入口。
  - 证据：部署清单、检查输出及审批记录。
- [ ] 全部旧实例和写流量已经停止。
  - 验证：实例清单中旧实例均为 `serving_traffic=false`，入口流量为 0。
  - 证据：实例状态、负载均衡摘除记录和写流量监控截图或导出数据。

### B. 数据库迁移（MySQL 强制门禁）

- [ ] AutoMigrate 已创建授权版本表和迁移状态表，索引、主键、非空约束及外键策略符合规格。
- [ ] 迁移进程取得数据库级锁，多实例不能同时推进迁移状态。
- [ ] 首次迁移已经持久化固定 `cutoff_user_id`，失败重试没有扩大存量集合。
- [ ] cutoff 范围内的 NULL 或非正旧版本归一化为 1，正版本保持原值。
- [ ] 幂等重试补齐缺行，且不覆盖新表中更高版本。
- [ ] 数量、缺行、版本相等和版本不倒退校验全部通过。
- [ ] 迁移状态为 `completed`，开始时间、完成时间和 cutoff 可查询。
  - 验证命令：
    `go test ./... -run 'TestMySQL.*AccessVersion(Migration|AutoMigrate)' -count=1`
  - 证据：测试日志、迁移日志、迁移状态查询结果和一致性查询结果。

### C. 认证与授权行为

- [ ] 迁移前签发且版本合法的 Access Token 在切换后仍然有效。
- [ ] 迁移前签发且版本合法的 Refresh Token 可通过
  `POST /api/refresh` 换取新 Token 对。
- [ ] 登录、Access Token 校验和 Refresh Token 校验只读取
  `user_access_versions`；新表缺行时拒绝 Token，不回退旧字段。
- [ ] 新用户首次登录会幂等初始化版本 1，并使用重新读取的版本签发 Token。
- [ ] 禁用、软删除、Kick、密码变化及授权关系变化均使用
  `EnsureAndIncrement`，旧 Access Token 和 Refresh Token 随后失效。
- [ ] 用户软删除和授权版本提升原子提交；恢复用户不会使删除前 Token 重新生效。
  - 快速门禁：
    `go test ./... -run 'AccessVersion|TokenVersion|Refresh|Kick' -count=1`
  - MySQL 强制门禁：
    `go test ./... -run 'TestMySQL.*(AccessVersion|TokenVersion|Refresh|Kick)' -count=1`
  - 证据：测试日志及关键 HTTP 请求/响应记录。

### D. 原子镜像与恢复流量（MySQL 强制门禁）

- [ ] 新表初始化或提升与 `users.token_version` 最终值镜像在同一事务提交。
- [ ] 任一主写或镜像写失败时两个存储均回滚，镜像失败指标增加。
- [ ] 恢复流量前，一致性扫描结果为 0 差异。
- [ ] 仅有新版本实例恢复流量，恢复后部署检查再次通过。
- [ ] 恢复流量后的登录、刷新、禁用、软删除、恢复、Kick 和授权变化冒烟测试通过。
  - 证据：事务失败注入测试、扫描结果、部署检查输出、实例清单和冒烟测试日志。

### E. 切换里程碑签署

## 二、加速耐久性资格验收

资格验收从切换里程碑通过并恢复流量后开始。资格窗口内旧字段只作为回滚镜像，
不得重新成为业务读取来源。本资格验收替代原完整发布周期和连续 7 个自然日观察门槛；
历史零散测试或已经停止进程的内存指标不得拼接为资格时间。

执行策略：事件触发，不设置固定执行时间。

- 每次用户要求开始本 Change 的任一剩余任务前，先运行关键认证授权回归、
  真实 MySQL 并发与事务门禁和一致性扫描。
- 前置门禁未通过时，不得开始对应任务。
- 每次结果按实际执行日期归档。
- 任务触发的前置门禁不能替代三小时加速耐久性资格验收。

- [x] 在 Windows 本地隔离真实 MySQL 与 Docker Redis 上连续至少 3 小时运行。
- [x] 至少完成 100,000 次混合认证授权操作。
- [x] 整个资格窗口维持至少 8 个并发工作单元。
- [x] 至少 3 次受控应用进程重启，外部运行器保留重启前后的累计结果。
- [x] 至少每 15 分钟、每次重启后和结束时执行扫描，一致性扫描差异数始终为 0：
  - cutoff 内用户必须存在新表记录且新旧版本相等；
  - cutoff 后已有新表记录的用户新旧版本相等；
  - cutoff 后旧字段为 NULL、0 或 1 的未初始化缺行不计差异；
  - cutoff 后旧字段大于 1 但新表缺行必须计为差异。
- [x] 非预期镜像写失败数为 0。
- [x] 成功签发 Token 后新表缺行数为 0。
- [x] `EnsureAndIncrement` 完成后新表缺行数为 0。
- [x] 原子回滚故障注入通过，新表主写、旧字段镜像和用户生命周期更新没有部分提交。
- [x] 登录、Access Token、Refresh Token、黑名单和失效后 Token 拒绝混合流量通过。
- [x] 关键认证授权回归、真实 MySQL 并发与事务门禁和真实 Redis 组合门禁通过。
- [x] 停机回滚步骤已演练；回滚前必须先完成一致性扫描。
  - 证据：JSONL 运行记录、汇总报告、扫描结果、重启记录、故障注入结果、测试日志
    和演练记录。

## 四、失败判定与回滚边界

- 切换前迁移或校验失败：保持旧实例和写流量停止，修复后沿用同一 cutoff 幂等重试。
- 观察期故障：停止全部新实例和写流量，完成一致性扫描后，才可整体回滚到旧版本。
- 退出版本部署后：只能回滚到读取新表且不依赖旧列的版本。
- 物理删列后：恢复旧字段需要独立数据库变更，不属于常规应用回滚。

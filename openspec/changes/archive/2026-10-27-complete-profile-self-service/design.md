## Context

本设计落实用户已确认的 Q1～Q17，不重新选择产品范围。`proposal.md` 说明动机；两份 delta 是目标行为，当前主规格仍记录现状。

静态核对依据：

- `web/src/pages/ProfilePage.tsx` 只 GET 本人资料并展示，无编辑操作；个人页维护本地 user，顶栏使用 Session context。
- `web/src/lib/api.ts` 当前会把非空 body 编码成 JSON；头像上传要求 multipart 的唯一 `file` 文件字段。不能在页面绕开集中 Client 自建 fetch。
- `UserAvatar` 在 `WorkbenchShell.tsx` 内按用户 ID 请求公开图片并持有 blob URL；同一用户更新时 ID 不变，现有 effect 不重新取图。服务端用户头像公开缓存 300 秒、默认头像 86400 秒，无可公开使用的版本或 ETag。
- `session-state.ts` 已有 `reloadContext()`、发起代际检查、Cookie 退出及退出待确认流程；重读 context 不等同于 Refresh。`UnsavedGuard` 已有导航／后退／beforeunload 和 busy 保护，局部编辑区切换须覆盖同样的放弃语义。
- Identity Repository 已把真实缺行映射为既有 `ErrUserNotFound`，真实故障原样返回；`UserService.Get`、UpdateSelf 和 ChangePassword 却把所有用户读取错误压成不存在。纯昵称保存后通过 Get 回读，写入可能已提交。
- `validatePassword` 在注册与改密间共享，现有 HTTP 声明的字符上限不能代表 bcrypt 的 72 字节能力。生产 Password Adapter 原样传入 UTF-8 字节，不做预哈希或截断。
- Go 配置已经校验 `file_upload.avatar_max_size_mb`；头像文件和标准化输出受此上限约束，multipart 总量已有额外 256 KiB 开销。主规格相关措辞和上传描述遗漏 WebP 需对齐现有行为，不能借此削弱校验。

以上是源码／规格事实，不是本 Change 已完成运行验收的声明。CLI context 中仍出现的退役顶层技术目录不作为恢复这些路径的依据；沿用 `internal/identity` 的 HTTP Adapter → Application → Repository／基础设施 Adapter，App 为唯一组合根。

## Goals / Non-Goals

**Goals:**

- 已登录且身份有效的用户，无需管理权限即可完成自己的昵称、头像和密码维护。
- 三个区域独立提交、一次只编辑一个；真实保存、失败、未知结果、显示刷新与退出清理准确区分。
- 当前标签内个人页与顶栏保持一致；敏感输入和晚到结果不能跨用户／登录会话泄漏。
- 补齐只读大小规则、用户读取错误分类和新设密码真实边界，迁移全部受影响调用者，不新建平行契约。

**Non-Goals:**

- 不增加邮箱交互、管理端代改、图片编辑器、资料广播、CAS／编辑锁、通用表单框架或新的状态库。
- 不更换密码算法，不重置历史密码，不收紧登录／旧密码校验，不扩展上传配置管理。
- 不改变 JWT／Cookie／Redis 会话协议、数据库表列、MinIO bucket、权限码或授权版本归属；不顺带修复其他清理／遥测问题。
- 本轮不在实现前同步主规格；完成实现和真实验收后，按任务 9.3 将已确认的 `user-management`／`admin-workbench` 增量同步到主规格，不修改既有归档证据。

## Decisions

### 1. 保留单页，以一个局部编辑状态管理三个独立操作

保留 `/profile`、现有主题与账号菜单，不新增设置路由、编辑 Dialog 或 Drawer。默认展示资料，各区域通过按钮页内展开。页面拥有 `activeEditor = none | nickname | avatar | password`、当前区草稿及提交状态；可按现有约定提取私有 Hook，但不引入全局表单层。

- 昵称只 PUT `{nickname}`，不序列化整个 UserInfo，避免携带邮箱触发密码校验或携带 avatar 被拒绝。客户端拒绝空／纯空白和超过 100 个 Unicode 字符，保留原始输入、不提供清空；后端其他合法调用者的邮箱或原值保存规则不收紧。
- 无真实变更时不伪造已保存；原有数据不足以保存时显示字段提示。取消恢复当前已确认值，完成保存后更新基线。
- 有草稿才询问切换／导航，取消放弃确认时完整保留编辑。局部区域切换复用同一放弃语义，不能只依赖路由 blocker。busy 期间禁用重复提交和区域切换，沿用既有离开保护，不承诺能阻止强制关闭浏览器。
- 昵称和头像草稿只在本页面内存；刷新或真正离开不持久化。身份变化清理草稿，不能带入新用户。

不选整页统一保存：三个 HTTP 操作没有跨请求事务，统一按钮会暗示不存在的原子性。也不允许多区同时编辑，避免改密完成后隐性丢弃另一区草稿。

### 2. 用只读 Identity 路由提供实际头像上限，失败局部隔离

新增 `GET /api/user/avatar-upload-policy`，在 Identity Descriptor 声明 Authenticated，由 App 统一注册，使用当前 Bearer 身份与既有四字段信封；成功 `data` 仅含正整数 `max_bytes`。HTTP Adapter 复用已注入且启动时验证的 `avatarMaxBytes`，与上传路径使用同一值。响应 `Cache-Control: no-store`，不增加配置项、数据库、Policy Repository 或配置管理页面。

客户端为规则维护独立的 loading／ready／error 状态，校验值为可安全使用的正整数字节数。不硬编码当前仓库的 2 MiB、不从用户名或 Token 推断规则，不把缺失值退回默认上限。有效规则到达前只禁用选图与上传，提供重试；当前图片、恢复默认、昵称与密码不被这次局部失败禁用。真实 401 或停用等认证终态继续由统一 Client 处理。

只输出大小上限，不扩成完整配置快照。JPEG／PNG／WebP、静态图片、像素和内容规则沿用现有契约，服务端保持最终判断。`max_bytes` 是原文件及标准化输出上限，不是 multipart 整包上限；既有额外 256 KiB 总量开销保持有界。

实施时确认现有 Seed 会为全部非公开接口派生权限，并已由用户选择按访问等级修正：新建 API 元数据仅对 `PermissionControlled` 派生权限编码，权限同步也只接收该等级；`Authenticated` 仍保存 `need_auth=1`，不自动创建权限编码或权限记录。规则适用于以后新增的纯登录接口，不按本路由 URL 特判。现有 API 管理字段、历史权限和授权关系不回填、不删除，原有 Seed／Finalize 职责保持不变；回归覆盖新建等级差异及存量保留。

不选前端常量或新的用户配置字段：常量会随部署漂移，上传能力也不是 User 的持久化资料。单独只读路由可以满足局部失败隔离，不把规则获取绑进认证启动成功条件。

### 3. 头像预览与真正写入分离，扩展既有 Client 的 FormData 通路

集中 Client 接受原样 FormData，不 JSON.stringify，也不手动设置 multipart Content-Type／boundary；继续使用既有认证桥、信封、原生图片入口与错误本地化。页面不自建认证传输层。

本地 File 与 preview object URL 属于当前编辑区；选图不发写请求、不改变顶栏。依据已取得的上限做原文件字节数和基本格式／空文件提示，服务端仍负责扩展名、MIME、解码、动画、像素及输出校验。取消／真正离开／身份变化释放预览资源。保存明确成功后退出预览状态，使用服务端受控图片，不把本地未标准化预览当成正式结果。

恢复默认是独立的即时写操作：先确认，确认才 DELETE，无请求体；取消不改变服务端或当前草稿。成功才丢弃当前选图并显示默认。失败或结果未知不声称默认已生效，不自动重发。

不引入裁剪库、图片安全解析器、外部地址导入或上传配置编辑；只对齐现有真实接口。

### 4. 资料显示从服务端确认，图片刷新显式覆盖缓存与异步次序

昵称／头像写入成功响应带 UserInfo；共享认证资料以真实 context 为准。优先复用 `reloadContext()` 更新顶栏，并把最新的可信用户投影同步给个人页；若实现需局部回填，只更新展示资料，不能用旧 `role` 字段推导或覆盖授权角色、权限、菜单。不得为了显示更新调用 Refresh、替换 grant 或重建会话。

为当前用户头像提供明确的刷新触发。保存／恢复默认成功及重新进入资料页重读显示时，个人页与顶栏触发新受控图片读取；仅重新渲染相同 ID 或重新使用旧 blob URL 不构成刷新。新取图使用显式绕过旧缓存的请求选项或等价的非敏感内存修订标识，并拒绝晚到旧图片覆盖新显示。其他用户图片保持正常缓存，不全站禁用图片缓存。

不暴露或借用头像 SHA-256、MinIO object key／ETag；不新增后端头像版本、持久化资料、跨标签广播或轮询。其他标签在重新进入个人资料／刷新时重读，而非监听资料事件。

服务端仍是最后实际写入成功的值，不按客户端响应先后定义新旧。当前编辑区和重读／取图有各自操作轮次，较早读取不能覆盖较新的确认结果；其他设备未保存草稿不自动重新提交。

### 5. 区分用户缺失、真实故障及提交后回读失败

保留既有 Repository 以 `ErrUserNotFound` 表示真实缺行的接口。Application 通过 `errors.Is` 区分该信号与真实错误：只有已确认不存在沿用认证拒绝，其他错误包装既有 `CodeInternalError`，HTTP 为 `500 / IDENTITY_INTERNAL_ERROR`、null data，不含 SQL、连接或驱动原因。不得导入 GORM 到 Application，或建另一套 NotFound／错误映射。

核对 UserService.Get、UpdateSelf、ChangePassword 及共享 Get 的管理端等消费者；受影响旧断言／Descriptor／说明一起迁移，不只为新页面绕过 401。保持已提交后回读与事务回滚的区别，不为了返回 500 而改变写入原子性或伪造回滚。

前端只将明确 200 作为已保存；其后的 context／图片重读失败显示“已保存，显示更新未完成”并提供只读重试。写响应丢失或服务端回读故障导致无法确认结果时保留适用草稿、显示结果未确认，可手动重新读取核对；不重发写入、不自动恢复旧值，也不把真正 401 当普通故障忽略。

### 6. 新设密码共享真实字节策略，保留旧验证与错误优先级

注册和改密共享现有 Application 密码策略，加上 `len(UTF-8 bytes) <= 72` 的设置上限；HTTP 和前端继续满足现有至少 6 个字符、大小写／数字／符号四类至少三类、确认一致及新旧不同。前端按 UTF-8 字节验证，不用 JavaScript 字符串长度或 `maxLength` 冒充字节数。

超出新设字节上限在 Hash 前成为 `422 / IDENTITY_VALIDATION_INVALID`，复用已有 `IDENTITY_PASSWORD_INVALID` 字段原因；清除 DTO／前端／OpenAPI 中会将该输入错误先拦成不同上限或暗示支持 255 字符的冲突声明。结构性缺字段／最小字符数等原 HTTP 400 分层保留。字段信息在注册定位 password，在改密正确关联新密码输入，不新增顶层错误码或复杂校验框架。

保留当前确认匹配、密码策略、新旧不同、用户读取、旧密码比对、Hash、事务更新的判定顺序。改密与授权版本提升仍同事务，真实失败不改密码／版本；该用户所有旧版本 Access／Refresh 在后续使用失效。普通昵称／头像不提升版本。

不选客户端独自限制、截断、预哈希或更换算法：前者不能保护其他设密入口，后几项会改变密码语义或带来迁移。不得给登录、旧密码比较增加新设密码的长度／复杂度限制。

### 7. 密码草稿是非敏感编辑保留机制的明确例外

三项密码仅在当前编辑内存与必要的进行中请求中使用，不进 Web Storage、Cookie、URL、导航状态、日志或错误回显。普通字段校验失败保留输入供修正；取消编辑、确认切换／真正离开、会话进入 recovery-required／logout-pending／unavailable／anonymous 或身份改变时清空。

取消导航确认并没有离开，仍保留当前输入；临时续期故障但 Access 仍有效也不误当失效。真正挂起后，即使同 SID 恢复且页面实例仍挂载，密码也不能自动回填或重交，昵称／头像的非敏感草稿则沿用原机制。

清理指清空表单值与应用持有的引用，不声称能擦除 JavaScript 引擎、浏览器或已发送网络缓冲区。浏览器自身密码管理器不在本 Change 范围内。

### 8. 改密成功与 Cookie 退出清理分阶段，始终检查发起者

每次读取或写入在发起时记录不可变的用户 ID、登录会话 SID 和局部操作轮次；响应回来先验证当前归属与轮次，再改展示、关闭编辑、导航或发起退出。当前同 SID 的正常续期不等于换用户；新 SID／新用户或已废弃的编辑请求不得接受旧结果。尤其不能在旧改密回调里无条件调用 logout 并退出新用户。

改密 200 是已改密码的证据，立即清密码并记录不含凭据的成功提示。仍属于当前发起者时调用现有 Session logout，经已有认证锁／状态锁、退出意图和 Cookie 清理完成后进入登录页；不伪造 401 触发清理，不在页面绕过协调调用 Logout。

如果退出失败，复用 logout-pending，文案同时说明密码已修改与服务器退出未确认，提供既有重试退出和显式登录，不重新改密、不保存新密码以自动登录。成功原因仅通过当前生命周期的既有 notice／导航消息承载，必要时最小扩展退出的原因传递；刷新后既有持久化退出标记仍生效，不新增成功凭据、资料存储或认证 key。

改密响应丢失／结果不明时没有成功证据，不执行“确认改密成功”的退出分支、不自动尝试新旧密码；提供结果未确认和手动重新登录核对的说明。明确认证终态仍由全局机制处理。其他独立设备只承诺后续认证拒绝旧版本，不新建实时踢出通知。

### 9. 回归与真实验收通过同一接口，规划不冒充证明

永久回归只覆盖消费者可见的输入边界、错误分类、事务／授权不变量与状态转移：Unicode 昵称／UTF-8 字节差异、真正不存在对比真实故障、写已提交后回读失败、FormData 真正可被后端识别、原生图刷新、密码清空和旧发起者隔离。不新建文案快照、源码匹配或只验证转发／mock 回声的测试。

实施阶段先保留可失败的错误分类／超长密码回归，再最小修正。复用现有测试依赖和集成夹具；统一执行受影响及完整后端、前端测试与构建。真实验收使用隔离 MySQL／Redis／MinIO 和真实 App／HTTP，浏览器验证亮暗、窄屏、键盘、文件选择、未保存保护、会话挂起与跨标签换用户；Cookie 退出失败须真实观察，不用组件 mock 冒充。

针对保存后回读故障，须精确触发认证／提交之后的真实读取失败，并观察已保存值和授权版本；不能仅把数据库在请求前关闭、在 Auth Middleware 就失败后宣称覆盖。运行所需额外既有依赖一并隔离，不读写生产；所有环境缺口如实报告，不勾选未执行验收，不保存密码、Token、DSN 或原始存储错误。

## Risks / Trade-offs

- **共享错误分类改变管理端等既有回读结果** → 在实施前用引用查询映射调用者，迁移全部行为断言；真实不存在与管理保护规则不变，不抑制 401。
- **UTF-8 字节与字符长度混淆** → 前后端各按正确量纲验证，以多字节边界回归；不靠截断或只改提示掩盖 Hash 失败。
- **图片公开缓存与本地 blob 留存** → 显式当前用户刷新、丢弃旧轮次、释放 object URL；服务端受控读取可能依法返回默认图，不能把默认回退或网络失败伪装为原上传图已显示。
- **策略读取与上传间部署上限变化** → 前置值仅作提示，服务器仍最终校验，413 保留草稿并允许重新读取；不为此增加规则版本或分布式事务。
- **多个设备同时编辑会覆盖先前写入** → 明确最后实际写入语义，保留手动重新读取，不声称有 CAS 或撤销。
- **改密成功但退出失败／回调晚到** → 分阶段状态和发起者检查，复用待确认退出，不撤销新登录、不误报密码修改失败。
- **敏感草稿例外影响原同会话恢复直觉** → 只清密码，非敏感草稿与页面实例继续按原规格保留，并向用户说明需重新填写。

## Migration Plan

1. 无数据库、授权版本存量、Redis key 或 MinIO 数据迁移；不批量重登／重置密码，不改现有签名密钥和 Cookie 范围。
2. 先交付后端新只读规则、错误分类、共享设密校验及同一 Snapshot 的文档，再发布依赖它的前端。后端先部署兼容旧显示页；前端遇缺失规则明确禁用上传，不猜测默认值。不得把回退常量当兼容通道。
3. 后端回滚会恢复本次修正的旧错误行为；需回退依赖新规则的前端或保持上传显式不可用，不能要求用户误信可上传上限。已成功改密仍有效，不回滚凭据或降低授权版本，不重放未知写请求。
4. 实际证明后更新 README、用户管理／配置与认证相关说明、原有 TODO 的立项与完成状态；仅当确有难撤销架构取舍时补 ADR，不为了形式新建空文档。
5. 实施与真实验收完成后同步 `user-management`、`admin-workbench` 主规格并严格验证，再单独执行提交／归档流程；不修改既有归档验收记录。

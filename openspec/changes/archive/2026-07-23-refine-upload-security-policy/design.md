## Context

现有上传体系已经按 `PurposeManagedFile` 和 `PurposeAvatar` 区分管理员普通文件与用户头像，但共享的类型注册表仍使管理员普通文件验证器接受 JPEG、PNG、WebP。管理员文件详情还会为通过验证的图片生成预览 URL，而头像已经有独立的标准化、存储和读取链路。

当前系统只保存类型、大小和验证状态，尚未保存实际写入对象的内容摘要。因此可以证明“上传时通过了格式策略”，但没有可供后续完整性比较的稳定内容指纹。

本项目仍处于初始版本阶段。本次优先收窄入口职责和攻击面，不引入 Office 解析器、外部扫描服务或新的完整性检查 API。

## Goals / Non-Goals

**Goals:**

- 管理员普通文件只接受 PDF、UTF-8 TXT、UTF-8 CSV。
- JPEG、PNG、WebP 只进入用户头像链路，并继续在写入前完成标准化。
- 管理员普通文件只提供附件下载，不再产生图片预览能力。
- 对实际传给 MinIO 的字节计算服务端 SHA-256，并与对象元数据一起持久化。
- 允许既有记录没有摘要，避免启动时批量读取对象存储。
- 保持现有 handler → service → model/dto/utils 分层、路由、权限码和 bucket 不变。

**Non-Goals:**

- 不支持 DOC/DOCX、XLS/XLSX、PPT/PPTX 或其他 Office 格式。
- 不引入 ClamAV、沙箱或第三方恶意文件扫描。
- 不解析 TXT/CSV 的业务字段，不判断 PDF 的业务内容是否可信。
- 不使用 SHA-256 作为病毒检测、对象名称、唯一约束或自动去重依据。
- 不新增手动完整性检查接口，不执行后台批量巡检，不在上传后重新读取 MinIO 做即时回读比对。
- 不自动删除、转换或重写历史 MinIO 对象。

## Decisions

### 1. 按上传用途收敛白名单，而不是删除共享图片类型

共享类型定义仍保留 JPEG、PNG、WebP，因为头像验证和标准化需要这些类型。管理员验证器在扩展名、声明 MIME 和内容验证之外，增加明确的 managed-file 类型集合，只允许 PDF、TXT、CSV。

这样可以避免复制 MIME 和规范扩展名定义，同时保证“类型在共享注册表中存在”不等于“所有上传入口都允许该类型”。下载访问判断也必须使用管理员文件集合，而不是仅调用全局 MIME 查询。

备选方案是从共享注册表删除图片类型，但会破坏头像验证；另一个方案是为两个入口复制完整注册表，会增加策略漂移风险。

### 2. 保留管理员预览路由，但当前策略始终不授予预览能力

文件详情不再返回 `preview_url`。现有管理员预览路由暂不删除，以避免同时修改路由、API 元数据和权限记录；任何管理员普通文件访问该路由都返回现有的文件状态冲突错误，且不得打开或流式返回对象。

这保留了未来按明确业务需求重新设计预览的兼容位置，同时当前版本没有可被内联展示的管理员文件。

备选方案是立即删除预览路由。该方案攻击面更小，但会扩大本次变更到路由和权限元数据清理；当前让服务层统一拒绝即可满足安全边界。

### 3. SHA-256 计算绑定“实际持久化字节”

上传安全验证结果增加内部 `ContentSHA256`，格式固定为 64 个小写十六进制字符：

- 管理员文件在有界暂存过程中对写入临时文件的字节同步计算摘要；验证成功后 MinIO 必须读取同一暂存文件，因此摘要对应实际传给对象存储的 PDF/TXT/CSV 字节。
- 头像先完成完整解码、方向处理、缩放、去元数据和重新编码，再对规范化输出字节计算摘要；不得保存原始头像上传内容的摘要。
- 管理员重新验证从 MinIO 打开对象后，经过同一有界暂存和当前格式策略计算摘要；只有重新验证成功才更新摘要。

摘要由服务端计算，不接受或比较客户端提交的摘要。摘要计算不会替代格式验证，也不证明对象没有恶意内容。

备选方案是在 MinIO 写入完成后立即回读对象并比较。它能覆盖更多存储链路故障，但会使每次上传增加一次完整对象读取，本次只建立基线，后续巡检再按业务需求增加回读比较。

### 4. 摘要与业务元数据原子持久化

数据模型增加：

- `model.File.ContentSHA256` → `files.content_sha256`，`varchar(64)`，允许空值语义，不加唯一索引；
- `model.User.AvatarContentSHA256` → `users.avatar_content_sha256`，`varchar(64)`，允许空值语义，不加唯一索引。

管理员文件记录创建或重新验证更新时，摘要与规范 MIME、状态、策略版本、验证时间一起写入。管理员文件元数据响应可以返回 `content_sha256`，便于后续人工或工具建立比较基线。

头像摘要与 object name、规范 MIME、验证状态和验证时间在同一次用户记录更新中提交。恢复默认头像时同步清空摘要。用户资料、头像读取响应、对象路径、普通运行日志和审计元数据均不返回头像摘要。

数据库写入失败时继续沿用现有补偿策略：明确未提交才删除新对象，提交结果不确定时不删除可能已被引用的对象。摘要字段不得改变该事务边界。

### 5. V1 初始策略直接收敛，不引入 Office 或扫描能力占位实现

项目尚处于初始版本，`file-upload-v1` 直接定义为最终的当前策略：

- managed file：PDF、UTF-8 TXT、UTF-8 CSV；
- avatar input：JPEG、PNG、WebP；
- avatar stored output：JPEG 或 PNG。

Office 和外部扫描只保留在后续优化建议中，不保留不可达解析代码、配置项或占位依赖。未来若在已发布环境扩大类型范围或引入扫描，应创建新的 OpenSpec change，并提升策略版本。

### 6. 历史数据采用非破坏性兼容

GORM AutoMigrate 只新增两个摘要列。既有文件和头像摘要允许为空，不在启动时读取 MinIO 补算摘要。

为避免旧策略下的管理员图片继续被视为当前允许类型，迁移只把 `validated` 且规范 MIME 不属于 `application/pdf`、`text/plain`、`text/csv` 的管理员文件降为 `legacy_unverified`。迁移保留对象、名称、原 MIME 和其他元数据，不删除或重写对象。

这些历史对象仍只能按现有历史文件规则作为 `application/octet-stream` 附件下载；管理员显式重新验证时，图片、Office 或其他不允许格式会变为 `blocked`，当前允许的 PDF/TXT/CSV 则写入摘要并恢复为 `validated`。

既有可信头像不因摘要为空而失效；用户下次成功上传头像时自然建立摘要基线。

## Risks / Trade-offs

- [摘要只在上传链路计算，不能证明 MinIO 中对象长期未变化] → 明确其为完整性基线；后续版本通过受控回读和比较实现主动检查。
- [保留预览路由形成一个当前无成功结果的接口] → 服务层在打开对象前统一返回冲突错误；后续确认不再需要兼容位置时再删除路由和权限元数据。
- [旧管理员图片降级后仍可作为历史附件下载] → 强制 `application/octet-stream`、附件语义和 `nosniff`；管理员可显式重新验证并将其封锁。
- [既有 PDF/TXT/CSV 摘要为空，完整性覆盖不是一次性完成] → 不做高成本启动扫描；通过新上传和历史重新验证逐步建立基线。
- [同内容摘要可能重复] → 不加唯一索引、不自动去重，避免不同业务记录错误共享生命周期。
- [继续使用 V1 名称会改变开发阶段旧数据对 V1 的理解] → 项目未形成稳定外部发布契约，并通过 MIME 定向降级处理旧管理员图片；正式发布后的策略变化必须提升版本。

## Migration Plan

1. 先增加 model 字段和 AutoMigrate 验证，确保已有数据库可无损新增摘要列。
2. 执行幂等状态回填：只将不属于新管理员白名单的 `validated` 文件更新为 `legacy_unverified`，不访问 MinIO。
3. 收窄 managed-file 验证与访问策略，并同步服务、DTO、OpenAPI 和测试。
4. 接入管理员文件和头像摘要计算、持久化及恢复默认头像清理。
5. 使用单元测试和路由/服务测试验证类型矩阵、摘要字节边界、历史状态和错误补偿。

回滚时旧代码可以忽略新增列；摘要列无需删除。被降级的历史文件不会自动恢复状态，如确需恢复旧策略，应在回滚版本中显式重新验证，避免直接批量改回 `validated`。

无。本次不定义摘要不一致后的自动封锁状态，因为主动回读比较不在当前范围内。
